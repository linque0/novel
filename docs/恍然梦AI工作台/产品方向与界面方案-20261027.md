# 恍然梦 AI 工作台：产品方向、界面与实现提案

日期：2026-10-27；状态更新：2026-10-28。**本文件作为旧方案、首版实现与调研档案保留。当前推荐主流程见 [共同创作模式重设计方案](共同创作模式重设计方案-20261028.md)。**

用户指出首版工作台的共同创作联动不足、阶段操作复杂。新方案明确由 AI 从空白开场并持续主导故事创作，手改为可选干预；同章工作稿与工坊共享，规划和审阅就地进行。新方案尚未实施。下面第 1–8、10–12 节记录原方向，第 14 节记录首版代码与机制验收，不作为新体验已经完成的证明。第 9 节书童研究与第 13 节 Skill 来源继续供查证。

## 1. 产品定位

让以 AI 承担大部分起草工作的作者，围绕一本书安排创作、检查结果、修订并管理连续性。

建议采用“一个小说工坊、同一作品库、两种工作台”：

- **写作工作台**：正文编辑优先，作者手写，恍然梦按需辅助。
- **恍然梦 AI 工作台**：章纲、生成候选和审修优先，作者负责创意决策与结果判断。

“独立”体现在完整导航、工作区和可单独打开的窗口；底层作品数据、正式正文、候选、人物设定、模型配置和版本记录共用。首版不另做需要导入导出或同步的独立应用。

工作台是可随时切换的视图，不把一部书永久标记为“手写书”或“AI 书”。一章可同时包含手写、AI 候选与人工修订，切换时不发生格式转换或作品复制。

沿用此前确认的边界：自动生成候选、逐章由作者采纳。AI 主力创作提高自动执行阶段的比例，不把模型审稿通过等同于作者采纳。

## 3. 用户任务与成功标准

首要用户：已有故事方向、希望 AI 起草多数正文，愿意审读、修改和控制剧情的长篇作者。也覆盖手写中遇阻后交给 AI 起草，以及把 AI 初稿转入精修的混合写作者。

用户打开工作台应立即知道：当前写到哪里、下一步可以做什么、哪些结果需要自己决定。首页默认回到上次章节或待处理结果，不强迫经过数据仪表盘。

成功标准：

1. 从一个故事念头或已有原稿进入可编辑的创作计划。
2. 作者能安排连续几章，离开生成页面后仍能查看进度与失败位置。
3. 审稿、修稿与候选比较围绕具体章节展开，不靠翻聊天记录找结果。
4. 在任意章节转入手写精修，再回 AI 工作台时，原文修改、待处理事项和来源版本正确呈现。
5. 全书只有一份正式正文；未采纳分支、后续计划与记忆事实始终区分。

## 4. 建议的信息架构

作品内导航采用以下六个入口，模型、Skill、预算和高级参数统一归入“创作配置”：

| 页面 | 用户在这里做什么 | 首屏主对象 |
| --- | --- | --- |
| 创作台 | 处理当前章节、下达本次任务、接手编辑 | 当前章纲/候选正文与下一步动作 |
| 故事规划 | 从前提、人物、世界规则到卷纲、章纲 | 计划内容，可切大纲树/现有画布 |
| 章节生产 | 安排连续创作、选择范围和处理异常 | 按卷排列的章节表 |
| 审稿与修订 | 审读、筛选问题、比较候选、决定采纳 | 一章正文及对应意见 |
| 作品资料 | 查看人物、设定、关系、伏笔与有效记忆 | 与当前章相关的资料和来源 |
| 运行与历史 | 看任务、暂停、恢复、追溯版本和用量 | 运行队列、阶段输出和恢复点 |

聊天成为随对象打开的“讨论”工具；讨论得到的结论可以明确转成章纲调整、作者指导或人物提案。聊天记录本身不成为唯一事实源。

## 5. 三个前端方向

共同设备假设：桌面优先，代表视口 1440×900，至少适配 1280×800。窄窗口收起辅助栏，当前正文保持可读；手机独立产品不在首版。

### A. 导演式创作台（推荐）

**北极星：作者始终看见正在创作的那一章，并能决定下一步。**

- 结构：窄导航 → 卷/章目录 → 中央章纲或稿件 → 按需打开的指导/审稿栏。运行进度以底部窄轨呈现，完整日志在运行页。
- 中央占主要宽度，阅读正文不与日志争位置；顶部只有作品切换、工作台切换和当前章阶段。当前任务的主动作只有一个，例如“按章纲起草”或“按选中意见修稿”。
- 字体：思源宋体 18–20px 用于稿件，现有无衬线字体 13–14px 用于控件。纸白底 `#F4F6F3`、雾青强调 `#275F66`、选中底 `#DFEBE8`，细描边和 6px 圆角；复用 OIcon。
- 主视觉是可读稿件、清晰的章号和审稿定位，不增加装饰插画。
- 收益：手写与 AI 起草共用阅读/编辑习惯；不足：全书批量状态需要进入章节生产页。

### B. 编辑部生产台

**北极星：一本书的生产状态一眼可安排。**

- 结构：模块导航 → 以卷章为行的生产表；选中章节后侧边抽出章纲、样稿或问题摘要，不常驻第三栏。
- 首屏直接显示待规划、待起草、待审、待采纳章节及下一步。支持范围选择、执行前预览和异常定位，正文在专注视图中阅读。
- 字体：无衬线为主，数字等宽；深石墨 `#1C2529`、铜橙 `#D9955F`、选中底 `#303C40`。通过列对齐和状态轨表达进度，避免满屏 KPI 卡片。
- 主视觉是章节行与连贯的阶段进度。
- 收益：适合连载与大批量安排；不足：容易让阅读和文学内容退到次要位置，不建议作为所有用户的默认首页。

### C. 故事演绎台

**北极星：先看见故事如何发展，再让 AI 写出来。**

- 结构：左侧作品资料 → 中央卷章/场景的空间画布 → 选中对象下方展开正文或指导。通过缩放与进入层级从全书走到场景。
- 首屏显示当前卷的故事线与场景安排；人物、冲突、伏笔直接挂接相关节点。保持现有大纲画布的操作语法。
- 字体：衬线章节标题、无衬线场景信息；冷瓷底 `#F1F0F7`、鸢尾色 `#66558F`、选中底 `#E4DFF0`。以细线、留白和层级表达关系，避免泛光和漂浮装饰。
- 主视觉是用户的故事结构，节点不伪装成流水线按钮。
- 收益：适合强规划、多线叙事；不足：新用户学习成本更高，不适合作为唯一的正文审读入口。

建议 A 为默认工作区，B 作为章节生产页，C 复用到故事规划页；三者不用做成三套互不相通的产品。视觉基调先选一种，之后统一所有页面。

## 6. 核心流程

### 新建一本以 AI 为主的作品

故事种子/参考资料 → AI 提出可编辑创作简报 → 作者确认关键方向 → 分步生成并确认人物、世界规则、卷章规划 → 选择第一章起草。

每步允许手动填写、局部重生成、暂缓或回退；只对后续任务真正依赖的内容提示缺口。已有作品按可用材料接入，不要求重新走立项流程。参考小说与作者原稿导入必须区分用途，不能混进同一正式正文。

### 连续创作

选择章纲范围 → 查看将生成的章节、依据和预算 → 连续起草/审修 → 在待处理队列审读 → 逐章采纳。原始候选、修订候选和作者实际采纳稿分别保留；严重矛盾与必要资料缺失暂停受影响分支。

### 手写转 AI

在写作工作台选中章节/位置 → “交给恍然梦继续” → AI 工作台带入同一章、选区及当前目标 → 生成候选 → 作者采纳或保留。返回时恢复原编辑位置。

### AI 转手写

候选可在 AI 工作台内直接精修，也可“到写作工作台精修”。未采纳候选进入明确的候选编辑状态，不静默变为正式正文。作者确认后，两边显示同一正式版本；修改原文导致旧任务过期时提示受影响范围。

### 两个窗口同时打开

一个窗口编辑某章，另一个窗口可阅读、讨论与生成独立候选；采纳和改正式正文遵守同一写入仲裁。切换编辑权必须显式完成，不能让两个编辑器轮流覆盖同一章。关闭窗口不等于批准或丢弃候选；完全退出应用保存检查点，重启后由用户恢复运行。

## 7. 功能实现方案

### 同应用、双工作台

- 在作品壳层增加 `writing/agent` 工作台视图，同一作品可记忆上次入口；书架提供两个打开方式。
- AI 工作台具备完整作品导航，可在主窗口打开，也可作为专用 Electron 窗口打开。它不再依赖聊天面板挂载后才能显示创作功能。
- 主窗口与独立窗口共用领域服务和数据源，避免第二个 IndexedDB、第二份作品和双向同步协议。

### 共用内容、拆开界面状态

- 共用正式正文、人物设定、章纲、候选、审稿、运行记录和模型配置；编辑位置、面板开合、视图布局按工作台/窗口保存。
- 采用明确的章节、候选和任务 ID 联动，避免把某个窗口当前选中的章节当作所有任务的隐含目标。
- 创作路线属于计划，已发生内容属于正文事实，未采纳候选属于分支；新界面保持现有语义边界。

### 从弹窗流程转成应用级服务

- 复用现有工作流、审修协议、阶段配置、记忆队列与 `airuns` 持久化能力。
- 将任务执行协调从“主窗口当前打开的作品”抽离为按作品 ID 调度；AI 窗口打开时，即使手写窗口停在书架，任务也有明确执行宿主。
- 将提案采纳从特定窗口的 `window.__ns.editor` 依赖中拆出。统一应用命令负责来源检查、富文本与保护标记、窗口锁、正文/任务事务、审计与撤销；可编辑界面共享同一规则。
- 区分作品状态、章稿状态和任务阶段；不能用一个“已完成”同时表达模型输出结束、审稿无问题和作者确认。
- 审稿台增加稿内定位、候选比较和逐段采用。未实现前整章采用仍必须保留旧稿并明确作用范围。

### 分期交付

1. **设计验证**：确认一种主方向，先做“有候选、有审稿、可切回手写”的代表页面原型，再展开其余页面。
2. **双工作台基础**：完整 AI 壳层、同作品切换与专用窗口；现有能力先迁入清晰页面，确保切换不丢稿。
3. **AI 主力闭环**：创作简报到章纲的引导、章节生产表、集中审稿修订、逐段比较与应用。
4. **运行与联动完善**：应用级调度、多窗口编辑权、异常分支、预算与恢复中心、全流程真实模型验收。

## 8. 首版验收重点

- 从书架直接进入 AI 工作台，能完成一章的规划、起草、审修和作者采纳。
- 手写/AI 工作台切换不复制作品、不改正文、不丢选区与未采纳候选。
- 任何位置的作者编辑都会正确使旧生成/审稿/分支失效，且保留旧产物供对照。
- 在手写窗口不打开目标章的条件下，AI 工作台仍能按规则申请采纳；遇到另一窗口占用时有清晰处理方式。
- 保存、取消、退出、重启、备份恢复后的状态可以解释，不出现后台继续使用旧正文写回。
- 使用真实配置的模型验证创作质量；固定响应只验证界面、状态和事务。

## 9. 本地书童源码研究：功能如何实现

### 9.1 研究范围与结论边界

本次从页面组件、状态推导、工作流命令一路追到 Electron 服务与数据库提交，重点查看真实调用关系，而不是根据 README 推断能力。也阅读了相关测试用例来理解预期边界；**本轮没有安装、启动或运行书童的测试，没有进行两项目的真实生成质量对比**。下列“源码事实”只说明当前代码的设计与执行路径，不构成运行成功或生成质量更好的证明。

书童采用 React、Zustand、CodeMirror、Electron、SQLite，并包含 LanceDB 检索依赖；恍然梦沿用 Vue、Pinia、TipTap、Dexie。学习重点是领域对象、状态关系与提交协议，不以迁移框架或存储引擎为前提。

核心判断：**书童最有价值的部分，是让每次生成成为有来源、有身份、有后续动作的作品产物。恍然梦应在此基础上强化作者随时接手，以及手写和 AI 主力创作共用一套正文的能力。**

### 9.2 阶段导航：从作品事实推导“下一步”，不只看任务状态

**源码事实。** `StageWorkspace` 根据标签类型装配设定、架构、蓝图、章节、历史、资料等页面；`stage-progress.ts` 的 `deriveStages`、`deriveChapters`、`chapterPhase`、`landingStage` 统一推导导航进度和章节动作。它不会简单把数据库的草稿状态当作全部流程状态：还要读取审稿记录、待合并修稿和最近合并时间。例如存在可合并修稿时显示“待合并”；过期修稿仍可查看，但不占据主流程。已有正文的作品也不会仅因架构未全部完成而强制回到架构页。

阅读入口：[页面装配](<F:/deepseek workplace/AI-Novel-Writer/src/components/stage/StageWorkspace.tsx>)、[章节与阶段推导](<F:/deepseek workplace/AI-Novel-Writer/src/stores/navigation/stage-progress.ts:54>)、[章级阶段映射](<F:/deepseek workplace/AI-Novel-Writer/src/components/stage/chapter/chapter-lifecycle.ts>)。

**对恍然梦的帮助。** 当前已有工作流阶段记录，但 AI 界面仍主要围绕聊天与弹窗组织。应增加一层共享的“章节创作视图模型”：由正式正文、候选、审稿、修稿、依赖有效性推导当前章的状态和建议动作，供目录、创作台、章节生产页共同使用。

**界面调整。** 目录显示“待起草／候选待审／意见待确认／修稿待合并／待采纳／正式正文”；生成中和已过期作为独立提示。手写章允许直接进入编辑或审稿，不要求补走 AI 流程。主按钮依状态变成“按章纲起草”“独立审稿”“按选中意见修稿”“比较修订”或“采纳正文”；始终允许作者选择其他合法动作。

### 9.3 从念头到章纲：可选择的领域步骤与分批提交

### 9.4 写稿：目标篇幅、可见正文续接与有限恢复

**源码事实。** `createChapterWorkflow` 通过 `GenerateDraftCommand` 执行写稿。命令装配作者材料、架构、人物、章纲、前驱原文、明确选入的候选和相关线索，再调用生成运行层。其篇幅控制并非只在提示词写一个字数：会统计可见正文、读取结束原因，按剩余目标有限续写；对输出被截断且几乎没有新增正文的情况，只给一次无进展恢复机会。超长时可做一次压缩尝试；若压缩未完成或不合格，可保留完整原稿。隐藏推理耗尽输出而未产生足够正文时，会停止并给出原因，而不是假装能续接隐藏推理。

### 9.9 连续创作：后章依赖具体前驱，不依赖“上一章最新结果”

**源码事实。** `createBatchChapterWorkflow` 将批次限制为 1–10 章、每步处理一章，冻结模型、目标篇幅和完成模式。源码同时支持 `draft_review` 与 `auto_finalize`，两者不是同一种行为：草稿待审模式不定稿、不执行定稿后处理；后章只显式选择同批直接前章候选，并验证 draftId、version 和 contentHash。恢复时读取原 batch 身份、已完成章节与当前运行句柄，跳过已保存部分；已有无关草稿、缺蓝图或前驱改变会阻止继续。

### 9.10 运行恢复与预算：持久产物和实际请求分别记账

**源码事实。** 页面层的工作流负责阶段顺序，实际生成有 Electron 主进程拥有的运行与请求服务。`generation-run-service.ts` 用 runId、invocationNonce、requestHash 去重；派发前持久化预留与派发标记，流式可见正文按 1 秒或新增约 4096 字节写快照，终止时再刷新。存储失败会阻止后续派发并保留可复制的未保存尾部；重启后不能确定供应商执行情况的请求保留未知状态，不直接当作没调用过再发一遍。恢复还要核对模型指纹、上下文快照和来源清单。推理展示和可保存正文走不同通道。

`planTaskBudget` 结合输入估算、模型/用户上下文与输出上限、推理计费边界、安全余量和根任务剩余预算，返回 ready、split-required 或 capacity-conflict。结构化条目允许按合同拆分；正文仅在支持显式分段候选时才可拆分，不能为适配预算悄悄减少作者目标。用量结算区分预留、已知实际与不确定负债。

阅读入口：[持久生成服务](<F:/deepseek workplace/AI-Novel-Writer/electron/services/generation-run-service.ts:103>)、[主进程生成所有者](<F:/deepseek workplace/AI-Novel-Writer/electron/services/main-generation-owner.ts>)、[任务预算规划](<F:/deepseek workplace/AI-Novel-Writer/src/services/generation/task-budget-planner.ts:231>)。

### 9.11 定稿与记忆：提交成功不因后处理失败变成失败

**源码事实。** `FinalizationRepository` 在同一个 SQLite 事务提交正文、定稿状态与发布 outbox；`FinalizationService` 随后将冻结正文发布成实体章节文件。重试只接收 finalizationId，从原提交记录取正文，不回读可能变化的编辑器内容。发布失败返回 committed=true 与待发布状态；相同请求复用已有提交身份。定稿后的知识库导入、剧情记录与角色状态更新又作为独立后处理步骤，按来源身份校验，并可按失败步骤恢复。角色更新区分明确身份的状态与待确认提案。

阅读入口：[定稿事务](<F:/deepseek workplace/AI-Novel-Writer/electron/repositories/finalization-repository.ts:196>)、[定稿与发布服务](<F:/deepseek workplace/AI-Novel-Writer/electron/services/finalization-service.ts:92>)、[后处理命令](<F:/deepseek workplace/AI-Novel-Writer/src/services/workflows/commands/finalize-chapter.command.ts:333>)。

**对恍然梦的帮助。** 恍然梦已在 Dexie 事务中把章节保存与记忆任务登记绑定，沿用即可；它不以实体 Markdown 为正式稿，因此不需要为模仿书童另加文件发布事实源。需要完善状态呈现和独立重试：记忆失败不撤回已采纳正文；再次修改或撤销后，旧来源任务不得迟到写入。新人物、身份关系和作者设定仍走提案确认。

**界面调整。** 采纳后先显示“正文已保存”，附属显示“记忆更新中／部分失败”；点击失败步骤重试，不要求重复采纳本章。两工作台显示同一任务记录，避免一边显示成功、一边把作品标记为整体失败。

**对恍然梦的帮助。** 当前已有阶段模型、预设和文本 Skill 快照，但配置存于应用级 `appconfig`。可增加作品级覆盖，继承全局默认；运行显示当次冻结内容，修改配置只影响后续运行。恍然梦允许的本地文本引用继续按自身受限读取机制处理，不照搬对方的包格式。聊天、按钮和批量入口统一调用领域命令，不另开能绕过确认的写入通道。

**界面调整。** 创作配置呈现“全局默认 → 本书覆盖 → 本次快照”；Agent 讨论中建议“调整第 8 章冲突”后，先生成章纲变更预览，作者确认才生效。只有真实任务登记成功才显示“已开始生成”，不把打开页面或创建文字说明当作执行成功。

### 9.13 伏笔与人物连续性：计划、发生事件和派生状态分层

**源码事实。** 叙事线索不只是一个“是否回收”字段：计划保存目标章节范围与作者意图，事件记录埋设、推进、解决或放弃以及正文证据。`use-plot-threads.ts` 分别生成计划候选和事件候选，通过确认入口生效；写稿命令再按当前章号、标题、关键事件和人物读取相关活跃线索，限量纳入上下文。角色连续性则保留 characterId、正式稿身份、字段预期版本和证据，不能仅靠同名推断是同一人物。

阅读入口：[线索计划与事件协议](<F:/deepseek workplace/AI-Novel-Writer/src/shared/narrative-thread-generation-pure.ts>)、[线索候选确认](<F:/deepseek workplace/AI-Novel-Writer/src/components/stage/plot/use-plot-threads.ts:699>)、[写稿读取活跃线索](<F:/deepseek workplace/AI-Novel-Writer/src/services/workflows/commands/generate-draft.command.ts:2002>)、[人物状态与来源协议](<F:/deepseek workplace/AI-Novel-Writer/src/shared/finalized-continuity.ts>)。

**对恍然梦的帮助。** 在现有伏笔、事件和人物阶段状态基础上，补齐“预定在哪章推进／正文实际在哪章发生／依据哪版原文”的联系。计划到期只能触发提醒，不能自动标记已发生；人物改名或同名仍通过实体 ID 识别。来源撤销后重算派生状态，保留作者设定的优先级。

**需要保留自身更严格的边界。** 书童线索事件的纯解析层使用去空白后的包含检查，这一步本身不足以提供唯一位置，也不足以证明事件判断正确。恍然梦应继续采用现有精确来源与位置验证，不因参考代码有检查就放宽要求。

**界面调整。** 故事规划页显示线索目标范围与进展轨；当前章的资料栏显示“本章计划推进”“最近一次正文依据”“可能久未推进”。作者可修改预定范围、确认事件或声明刻意延后；新线索与新身份关系仍是待确认提案，不在后台直接升为正式设定。

## 10. 源码研究对产品方向的具体修订

### 10.1 产品主线：作者导演，AI 执行，作品承载结果

推荐继续采用 A 导演式创作台，以下为研究后的深化建议，视觉方向仍待用户确定。

用户不必先判断该点哪个技术功能。进入当前章后看到正文/候选、当前目标、待自己决定的事项和下一步。单次运行可以自动串联多个生成阶段；遇到正式事实变更、意见确认、差异合并和正文采纳时，明确交给作者。作者也可从任何阶段转手写，不把“AI 流程完成率”作为作品完成率。

三个产品对象贯穿两工作台：

| 对象 | 作用 | 作者看见的含义 |
| --- | --- | --- |
| 计划 | 创作简报、卷章目标、场景和结束状态 | 将要发生，可以调整，不是已发生事实 |
| 稿件分支 | 手工候选、AI 初稿、修稿与人工合并稿 | 可比较和继续创作，未采纳不进入正式记忆 |
| 正式正文 | 作者采纳/正式保存的章节版本 | 本书当前正文，派生记忆必须绑定其具体版本 |

这里的分支先实现为有明确父候选与版本的稿件关系，不把首版扩大为任意复杂的全书分支树。手写正式编辑继续使用现有保存机制；“采纳”特指把候选应用到正文，不要求手写每次保存都重新审批。

## 11. 前端深化：把机制转成作者可操作的页面

### 11.1 创作台的代表首屏

以“第 8 章已有候选、审稿发现 2 个问题、作者正在决定修法”为代表内容，后续设计稿使用同一示例，不用空状态代替核心工作。

- 左侧：作品与工作台切换、六个模块入口；章目录显示章名、当前稿状态、是否依赖过期。
- 中央：章号、标题、当前稿件版本；正文是主要面积。章纲、正文、比较作为对象视图切换，避免章纲表单与全文并排挤占阅读区。
- 右侧：本次指导／审稿意见按当前任务打开；审稿中展示问题、原文、来源和作者选择。材料列表按需展开。
- 底部：窄运行条显示当前阶段、已保存检查点与停止/暂停入口，详情进入运行页。
- 采纳区：显示将影响的章节与当前正式版本；若另一窗口有未保存编辑，先展示冲突与接手方式。原稿始终可追溯。

“已定位引文”“模型认为已解决”“作者已采纳”使用不同文字。证据可定位不标成“事实已确认”，也不使用一个绿色勾表达所有通过。

### 11.2 启动任务：高级能力渐进展开

起草按钮附近的简洁启动层包含：本章目标、本次指导、目标篇幅、是否起草连续章节。默认继承模型与阶段配置，展开后可查看本次模型、材料、预算和规则快照。缺章纲直接补章纲；预算冲突显示受限原因和可选处理，避免让新用户先填技术参数才能开始。

连续创作使用章节生产页的范围预览，而不是在聊天输入框发送“帮我写十章”。作者确认的是生成范围与执行方式，不是提前批准十章正文。

### 11.3 审稿与修订：意见选择和正文合并分两次决策

第一次决定“处理哪些问题、作者有什么要求”，生成修稿候选；第二次决定“这些实际文字改动用哪些”。两次决策绑定各自的输入版本。人工合并完成后针对原问题复核，不能继续展示合并前的“已解决”结果。严重问题仍未解决时进入作者待处理队列；文风建议不伪装成连续性错误。

全屏审稿台和创作台右侧简版共享同一审稿与选择状态。进入手写工作台时可携带问题定位；返回后读取当前稿件版本，不从旧组件缓存恢复已过期判断。

### 11.4 运行中心：围绕结果与恢复组织

列表优先显示需要处理的情况：等待作者、资料缺失、候选过期、请求中断、记忆部分失败。展开一条运行后才看阶段、材料、冻结配置与用量。可复制的中断正文与最后持久化位置应直接可见；普通作者不必读完整日志才能恢复。

关闭工作台页面不等于取消运行；关闭应用按当前能力保存并中断，重启由作者恢复。若首版仍由主窗口宿主执行，应在实际生命周期内保证这一语义，不能仅改界面文案。

## 12. 功能实现落地与验证调整

### 12.1 统一命令入口，先解除界面依赖

拟在现有服务上整理以下领域命令，名称为设计建议，并非现有 API：

| 命令 | 输入要点 | 必须返回的结果 |
| --- | --- | --- |
| `startCreativeTask` | workId、章节/候选身份、输入版本、本次目标 | 已持久化的 runId、目标和实际启动状态 |
| `confirmReviewSelection` | 审稿身份、源稿身份、意见选择、作者要求 | 不可变的确认清单身份与版本 |
| `mergeCandidate` | 基稿、修稿、目标版本、逐块选择 | 新合并候选及其来源，必要时登记复核 |
| `adoptCandidate` | workId、chapterId、candidateId、预期正文版本、操作身份 | 保存后的正文版本、审计/撤销信息、记忆任务身份 |
| `resumeCreativeTask` | 明确 runId/checkpointId、原配置和来源校验 | 已复用产物或新请求身份；拒绝时返回具体过期原因 |

不能为让独立窗口采纳而绕开 `application.js` 直接修改 `db.chapters`。将现有正文应用能力抽成共用服务，并用共享的编辑会话/TipTap 文档处理层保留富文本、锚点、保护标记、写入锁与撤销审计。确认源版本、应用修改、正文保存和记忆任务登记必须仍遵循原有一致性保护。

同一 Electron 应用与同一 IndexedDB 是双工作台共用数据的前提；独立窗口按现有窗口模型接入相同应用会话，不能另开独立存储 partition 后再用同步补救。当前面板有模块/实体锁和主窗口关闭级联逻辑，新增完整 AI 窗口时要逐项调整生命周期，不能只增加一个窗口类型。

### 12.2 三种状态分别存储，界面统一推导

建议持久记录以现有 `airuns` 类型和 schemaVersion 扩展，不另设一套聊天事实库：

- 作品/稿件事实：正式正文版本、候选及父候选、依赖、采用与归档关系。
- 人工决策：审稿选择、作者补充、合并选择、采纳结果；明确绑定输入，过期后不能重用。
- 执行记录：阶段和请求身份、模型/规则快照、来源清单、检查点、预算与实际用量、错误和中断原因。

界面“待做什么”由这些记录推导，不能维护一份会与正文分歧的可写阶段百分比。长篇性能先用现有索引测量，逐章读取和分页；不要为了让导航即时显示而每次扫描全书正文。

### 12.3 调度方案选择

推荐先采用**应用级协调器 + 现有 Dexie 领域服务 + 持久租约**：按 workId 管理任务，两个工作台只提交命令和订阅状态。执行宿主与当前可见章节脱钩；切换作品不能把旧任务绑定到新作品。

书童的主进程请求所有权是后续可借鉴方向，但恍然梦的业务数据仍在渲染侧 Dexie。直接把整套工作流搬进 Electron 主进程会同时引入数据库访问与事务桥接问题，不作为本轮 UI 改造的必需条件。若以后迁移模型传输与请求账本，应单独设计“主进程持有请求、Dexie 确认领域提交”的回执协议，并先验证窗口关闭和异常恢复。

### 12.4 建议交付顺序

1. **先做可联动的独立创作台**：确定视觉方向；完成代表页面；按作品寻址；同一章/候选在两工作台切换；迁入现有规划、审修、候选、材料和记忆状态。独立采纳必须通过共用服务，不以“请先打开原编辑器”作为最终体验。
2. **再补从念头到正文的完整入口**：创作简报、人物/规则提案、分批卷章规划、章节生产范围预览和进度恢复，支持从已有作品中途接入。
3. **强化作者接手与审修质量**：章纲目标逐项核对、稿内定位、富文本差异选择、合并后定向复核、来源变化后的影响提示。
4. **专项强化长期运行**：流式尾部持久化、请求幂等与未知用量、多窗口宿主生命周期、作品级配置覆盖，以及长篇读取性能。

第二至四批可按依赖穿插，但第一批不能只有漂亮外壳而仍要求作者回聊天弹窗寻找任务。

### 12.5 新增验收情景

| 情景 | 应观察到的行为 |
| --- | --- |
| 手写第 8 章一半，转 AI 接写，再回手写 | 同一章节与明确位置；候选未采纳不改变正式正文；返回恢复编辑位置 |
| 书架停留时，独立 AI 工作台生成并采纳第 8 章 | 目标按身份解析，无需另一个窗口先打开该章；写入仍经过相同保护 |
| 审稿发现“人物已知秘密”但原文没有足够证据 | 标记待核实，展示实际来源；作者未选择的意见不进入修稿 |
| 章纲要求付出代价，正文只承诺以后偿还 | 目标检查不能仅凭关键词判完成；真实模型核验目标语义与误报 |
| 作者合并修稿时另一个窗口改了原稿 | 提交被拒绝或进入明确冲突，旧稿与修稿仍可比较；不静默覆盖 |
| 第 8 章候选被换稿，第 9–10 章已生成 | 后章标记依赖过期；重新校验前不能直接采纳 |
| 生成十章蓝图时后半批结构化输出失败 | 已验证和确认的完整范围保留，剩余范围明确；不把半条 JSON 当章纲 |
| 请求断网、终止响应丢失或本地写盘失败 | 保留持久正文/可复制尾部；区分未完成请求与已完成未应用产物，避免盲目重发 |
| 正文采纳后记忆提取失败，再编辑或撤销正文 | 已采纳正文保留；只重试合法失败步骤，旧来源任务不能迟到写入 |
| 改动模型、预设或 Skill 后恢复旧任务 | 说明原冻结配置与当前差异；不静默改模型继续同一运行 |

确定性测试验证来源、状态、事务和恢复；真实模型测试另外报告事实冲突、目标完成率、误报、修稿新增问题、作者编辑量、耗时和 Token 用量。上述场景是新增验收要求，不是本轮已经通过的结果。

本地 `LICENSE` 为 GNU GPL Version 3。本轮只做源码研究与独立方案编写，未复制其业务实现；以后若直接引入代码、组件或算法实现，应先核对项目许可及分发要求。优先独立实现其机制，保留清晰来源记录。

## 13. GitHub 写作与上下文记忆 Skill：筛选、接入和查证

### 14.2 手写和 AI 如何连接

`StudioWorkspace.vue` 同时保留两种工作台，将同一个 `EditorPane` 移至当前视图：切换保留 TipTap 实例、选区、撤销与滚动位置。正式正文在两种视图里是同一份数据。

**候选精修**单独使用候选编辑器。转入手写时明确选择候选对应章节与正文模块，保留“尚未写入正式正文”的状态；在手写目录改选其他章节会退出该候选，避免把 A 章稿件显示成 B 章内容。只有作者采纳才调用正式应用服务，并在保存正文的事务内登记记忆任务。

### 14.3 独立窗口和保存边界

完整 `agent` 窗口可以直接执行确定性工作流调度，模型请求继续使用既有 AI 服务与阶段快照；旧窄版聊天窗口继续走主窗口请求协议。

首版采用**同作品整部正文编辑权互斥**：打开完整 AI 窗口前，相关编辑器暂时停止输入并完成保存；整章锁与已有单章窗口相互冲突。其他窗口的正文只读，完整窗口关闭后重新读取数据库、重建正文编辑器并清除旧撤销历史，再恢复可写，防止旧正文覆盖新采纳稿。

新增目标章节编辑桥，采纳时显式准备对应章节，不再依赖作者预先打开正确正文。整章稿采纳校验完整规范化正文，支持多段落与重复段落；局部改写继续使用原唯一定位保护，受保护链接和批注仍阻止整章替换。

候选操作在点击时绑定运行、章节和候选身份，保存等待期间切换版本不会改换被采纳的稿件。运行保存失败后保留脏状态，定时刷新和跨窗口广播不能用旧数据库记录覆盖输入。临时移交失败只恢复原编辑器，不重载旧数据库正文。完整窗口关窗时冻结输入、等待本机运行中断，并保存到最新脏状态清空；失败或超时恢复输入并保留窗口与编辑锁，供作者重试。
