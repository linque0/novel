# 05 · 方案 C：把小说工坊做成 DSH 插件

> 结论先说：**可行，但这不是"打包一下"的事**。三条硬约束里两条有解、一条必须做产品取舍；在方案 B 完成前不建议启动。

## 1 · 插件的骨架长什么样（以催更姬为参照）

| 部件 | 催更姬的做法 | 证据 |
| --- | --- | --- |
| 包声明 | `package.json` 里 `main: runtime/index.js`、`exports["./client"]`、`dsh.bundle.patch: ./cordis.patch.yml`、`dsh.client.platform: web` + `inject` 客户端服务列表 | `package.json` |
| 服务端 | `export const name/inject/Config` + `apply(ctx, config)`，用 `defineTool` 注册工具、`registerSkills` 注册技能、`registerPrompt` 注入提示词 | `src/index.js` |
| 传输 | `registerRpcRoute` 挂 `/api` 的 `cuigengji/dispatch`，客户端用 `ctx.connection.rpc.call` 调 | `src/index.js`；`src/client/index.tsx` `RPC_ENDPOINT` |
| 客户端 | React 组件注册进 `ctx.slots`/`sidebarRightTabs`，带 `keepMounted`、`patterns: ['dsh-resource://cuigengji/**']` | `src/client/index.tsx` |
| 分发 | npm 包 + 宿主「插件 → 添加插件」；`files` 含 `src/lib/skills/runtime`，**普通用户不跑构建钩子** | `package.json`、`README.md` |

**所以"小说工坊作为插件"要交付的最小件**：一个 `dsh.bundle.patch` 的 cordis 补丁、一个服务端入口（工具/RPC/技能）、一个客户端入口（React 或 Web surface）、一个 Node 存储层。

## 2 · 三条硬约束

### 约束 1：数据在渲染进程的 IndexedDB，Node 侧工具读不到

- **证据**：`src/db/database.js` 全库是 Dexie；插件工具由 `defineTool` 在 **Node 进程**执行（`src/index.js`），两端没有共享内存或文件。
- **可解**：依赖方案 B 的 `adapters-fs`，把作品存到磁盘（或让桌面版与插件共享一个"作品目录"格式）。
- **不可解的部分**：**不能**让插件直接读浏览器 IndexedDB——除非把工具也搬到渲染进程，而 DSH 的工具面不在渲染进程。
- **工作量**：即方案 B 的 P5（10–16 人日），无法绕过。

### 约束 2：Vue SPA（18551 行）与宿主 React 插槽

- **证据**：`src/` 有 91 个 `.vue`（18551 行），入口 `src/main.js`；宿主插件客户端是 React（`src/client/index.tsx` 第一行 `import React from 'react'`），通过 `ctx.slots.register` 挂载。
- **解法一（React 壳挂 Vue）**：客户端入口里 `createApp(NovelStudioRoot)` 挂到宿主给的 DOM 节点。
  - 坑：Vue runtime 与被剥离的 `naive-ui` 一起进客户端 bundle（体积）；宿主主题变量与工坊四套皮肤的变量体系冲突，必须外层容器隔离；`keepMounted` 与 Vue 生命周期要对齐（`unmount` 时机）；工坊的全局样式（`src/styles`）需要加前缀或 Shadow DOM。
- **解法二（资源面板 + 隔离容器）**：把 `dist/` 交给宿主的资源通道（催更姬用 `dsh-resource://cuigengji/**` 声明 tab 的 URL 模式），在隔离容器里跑独立 SPA。
  - 坑：⚠️ **未核实宿主是否提供 iframe/webview 型 surface**（见 01 文档八节）。若没有，这条路不成立。
- **取舍**：解法一对"AI 与 UI 同屏协作"友好（能共享宿主会话），解法二对"少改代码"友好（SPA 原样跑）。**建议先做解法二的可行性核实**，再决定。

### 约束 3：两个 Agent 循环互斥（必须做产品取舍，不是技术问题）

- **证据**：宿主提供 `dsh-agent-loop`（`~/.dsh/profiles/node_modules/@deepseek-ai/dsh-agent-loop`）；恍然梦有自己的循环（`dialogue.js:283` `roundLimit = task ? 24 : 6`）与 22 类任务模板。
- **二选一**：
  - **(a) 保留恍然梦循环** → 插件退化成"第二个窗口壳"，宿主的会话/工具/子 Agent 都用不上，插件化的最大收益（复用宿主 Agent）归零。
  - **(b) 交给宿主循环**（推荐）→ 恍然梦的循环作废，但预设编译引擎与 22 类任务模板可保留为"提示词资产 + 工具化任务"，这正是方案 A 的产物：A1 的技能目录、A2 的上下文索引、A3 的幂等写入，在宿主循环下**恰好就是插件需要的工具面**。
- **结论**：**方案 A 不是方案 C 的替代品，而是方案 C 的前半程。** 先按 A 把能力工具化，再按 B 把数据下沉，最后一层壳才是 C。

## 3 · 最小可跑切片（MVS，建议先只做这个）

**范围**：只读 + 一个静态视图，不含写入。

1. 服务端：3 个只读工具 `studio_list_works`、`studio_read_chapter {cursor}`、`studio_search {query}`，数据来自只读快照（先用「导出/备份 JSON」当输入，不要求实时）。
2. 客户端：一个 tab，显示作品目录（可复用宿主表格/树组件，不引入 Vue）。
3. 不做：写入、画布、预设编辑、皮肤。

**MVS 要回答的三个问题**
- 宿主能否在 Node 侧稳定拿到作品数据（哪怕只是快照）？
- 宿主 agent 用这三个工具，能否完成一次"读设定 + 读上一章 + 续写一段"的真实任务？
- 客户端 tab 的样式/主题冲突有多大？

**工时**：8–12 人日（不含数据层重写）。

## 4 · MVS 与全量目标的差距

| 能力 | MVS | 全量目标 | 差距来源 |
| --- | --- | --- | --- |
| 数据 | 只读快照 | 实时读写 + 历史 + 事务 | 方案 B P5 |
| 工具面 | 3 个只读 | 对齐催更姬的 60+ action、强 schema、幂等 | 方案 A3 + 工具化重写 |
| UI | 一个目录 tab | 正文/大纲/设定/预设/画布 | 91 个 `.vue` 的宿主化，最大的一块 |
| 智能 | 宿主循环 + 3 工具 | 宿主循环 + 全套工具 + Skill + 预设编译 | 方案 A1/A2 |
| 协作 | 无 | 与桌面版共享同一作品目录 | 需先定"作品目录格式"契约 |

## 5 · 全量工作量与判断

| 工作块 | 估算（人日） |
| --- | --- |
| 方案 B（P1–P5，含方案 A 的 A3） | 29–46 |
| 工具面重写（对齐强 schema + 幂等 + 权限面） | 12–20 |
| 客户端宿主化（91 个 Vue 组件 → 宿主插槽/隔离容器） | 25–40（最大不确定性） |
| 预设引擎接入宿主提示词组装 | 6–10 |
| 分发/升级/迁移（对齐催更姬的 `upgrade.md` 那套） | 8–12 |
| **合计** | **80–128** |

**判断**：以"能跑"为目标 80 人日起；以"替代桌面版"为目标不现实（桌面版的四套皮肤、3D 书架、双窗、画布避让在宿主插槽里几乎无法等价复现）。**若目标只是"在 DSH 里也能写"，MVS + 方案 A 的工具面（20 人日量级）就够了，不需要全量 C。**

## 6 · 失败模式

| 失败模式 | 早期信号 | 处理 |
| --- | --- | --- |
| 宿主无隔离 surface | 解法二核实不通过 | 走解法一（React 壳挂 Vue），接受样式与体积代价 |
| 双宿主数据分叉 | 桌面版与插件各写一份 | 锁 + 单一可写宿主（见 04 §6） |
| 循环打架 | 会话里出现两套工具调用格式 | 永久只留 (b) 方案：宿主循环，恍然梦循环在插件里禁用 |
| 升级负担 | DSH 每次接口变动都要跟 | 只在 `cordis.patch.yml` + 稳定 API 上依赖，避免碰内部实现 |

## 7 · 明确不建议

- **不建议**为了插件化而把桌面版改成 Web 应用（网页版数据独立性说明 Dexie 方案对本地优先是优点，不是缺点）。
- **不建议**在方案 B 之前启动全量 C——那时所有 UI 与数据工作都会返工一次。
