# 03 · 方案 A：把催更姬的长处单向移植进小说工坊

> 目标：在**不改 UI 栈、不动 Electron 主进程、不引第三方依赖、不换存储引擎**的前提下，补齐恍然梦的四个结构性短板。
> 每一项都写成"可单独交付、可单独回滚"的切片；任何一项做完不影响其余三项。

## 0 · 总目标与成功判据

1. **上下文可缩放**：同一部 100 万字作品，"续写下一章"的输入 token 不再随全书线性增长（改动前由预设块全量拼装决定，改动后由索引 + 按需拉取决定）。
2. **规范可扩展**：新增一条写作方法论只需加一个技能文件，不改 `builtin-writing-skills.js` 的代码。
3. **并发可前置**：两次并发写入同一章时，第二次在**写入前**被拦下并提示重读，而不是靠事后 hash 发现。
4. **规划可回退**：一次批量画布操作（自动排布、批量移动、批量删除）可整批撤销，且撤销不污染后续改动。
5. **既有回归零退化**：`tools/*-unit-verify.mjs` 与现有 156 项纯逻辑回归全绿。

## A1 · Skill 目录化（渐进披露）

**现状**：`builtin-writing-skills.js` 里 4 段固定文本（planning/drafting/review/revision）随阶段整段注入（`memory-stage.js:12`），带 `provenance` 出处。想加第五种方法论只能改代码。

**目标形态**（对齐催更姬 `skills/*/SKILL.md` + `references/` 的渐进披露）：
- 技能 = `{ id, stage, name, summary, body, references[], provenance, enabled }`，内置技能仍在代码里（保持 provenance 审计），**作者自定义技能**存 Dexie 新表 `aiskills`。
- 提示词只注入 **技能索引**（`id + name + summary`，一行一条，按当前阶段过滤）。
- 新增两个工具：`list_skills {stage?,query?}`（返回索引，可检索）与 `load_skill {id}`（返回正文；`references` 按需二次加载）。
- 阶段默认技能仍自动注入正文一轮（保持现有行为），只有"额外方法论"走按需加载——这样既省 token 又不打断现有体验。

**改动落点**：`src/services/ai/builtin-writing-skills.js`（改为注册源）、新增 `src/services/ai/skills.js`（目录/检索/加载）、`tools.js`（+2 工具）、`prepare-dialogue.js`（技能索引进槽位）、`db/database.js`（+1 表 `aiskills`）、`db/ai-repo.js`（CRUD）、AI 设置页 +1 个技能管理 tab。

**风险与回退**：阶段注入体积变化会影响既有 `stage-budget` 预算断言 → 回退开关 `aiSkills.mode = 'inline' | 'catalog'`，默认 `inline`（行为不变），作者切换后才生效。

**验收命令**
```bash
node tools/builtin-skills-unit-verify.mjs      # 既有：内置技能结构
node tools/builtin-skill-sources-verify.mjs    # 既有：provenance 出处
node tools/stage-budget-unit-verify.mjs        # 既有：阶段预算
node tools/skills-catalog-unit-verify.mjs      # 新增：索引/检索/加载/开关
npm run build
```
**工时**：3–5 人日。

## A2 · 上下文检索化（索引 + 按需拉全文）

**现状**：`prepare-dialogue.js:106` 用 `compilePreset` 拼装全部槽位，再 `fitBlocks` 按 `inputBudget`（默认 10000）裁剪。**被裁掉的内容模型永远看不到，且不知道自己被裁了**。

**目标形态**（对齐催更姬"先摘要索引、再按需读全文"）：
- 预设槽位继续负责"骨架"（作品概况、当前章锚点、本次指令、输出协议）。
- 世界书/人物卡/前情/知识卡改为注入 **目录 + 命中摘要**（每条一行：`id｜标题｜一句话摘要｜更新时间`），正文由模型调用既有 `read_document`/`search_book`/`get_character` 按需拉取（这些工具已支持 `cursor`/`limit`，不必新增）。
- 新增运输层提示：注入末尾固定一行"被折叠 N 条，可用 search_book / read_document 展开"，把裁剪从"静默丢失"变成"可发现"。
- 保留 `inputBudget` 与 `fitBlocks`：预算现在只约束骨架与索引，不再约束整批正文。

**改动落点**：`prepare-dialogue.js`、`memory-stage.js`、新增 `src/services/ai/context-index.js`（把现有 `booksource.js` 的清单能力整理成"索引行"）、`contracts.js`（分页/截断约定复用）、设置页新增「上下文模式：全量 / 索引」（默认全量）。

**风险与回退**：作者最直观的感受是"AI 好像没看我写过的设定" → 回退：默认 `全量`，只有作者显式切到 `索引` 才变行为；切换时给出一次性说明（哪些内容改由工具按需读取）。

**验收命令**
```bash
node tools/creative-retrieval-unit-verify.mjs   # 检索与召回
node tools/story-context-verify.mjs             # 上下文装配
node tools/knowledge-verify.mjs                 # 知识卡
node tools/context-index-unit-verify.mjs        # 新增：索引行生成/折叠计数/预算
npm run build
```
**工时**：5–8 人日。

## A3 · requestId 幂等 + expectedRevision 前置校验

**现状**：写入靠 `proposalGuard` 的 `entityHash`/`sourceHash` **事后**比对；并发时结果是"写完了才发现来源变了，回滚"。租约（`ai-repo.js:42`，TTL 120s）只保护知识库任务，不保护正文写入。

**目标形态**（对齐催更姬 `requestId` + `expectedRevision`）：
- 每个实体（章/人物/设定/大纲节点）维护单调 `revision`（整数），任何写入 +1。
- 写入请求携带 `{ requestId, expectedRevision }`；
  - `requestId` 命中 `airequests` 表 → 直接返回上次结果（重试不重复创建/覆盖）；
  - `expectedRevision !== 当前` → 返回结构化冲突（`{ conflict: true, currentRevision, currentHash }`），**不落库**，由作者或 Agent 重读合并。
- `entityHash` 保留为第二道校验（内容级），与 `revision` 分工：`revision` 管"别人动过"，hash 管"内容确实一致"。

**改动落点**：`db/database.js`（`db.version+1`：新增 `airequests` 表与各实体 `revision` 字段）、`db/ai-repo.js`（请求表读写 + `expectRevision` helper）、`application.js:101`（`applyProposal` 入口）、`task-application.js`、`dialogue.js`（把 requestId 透传到输出工具）、`contracts.js`（冲突对象）。

**风险与回退**：Dexie 迁移必须幂等且只增不删；`revision` 缺失视为 0。回退：`aiConcurrency.mode = 'hash' | 'revision'`，默认 `hash`（现行为），迁移完成并跑过并发回归后切 `revision`。

**验收命令**
```bash
node tools/writing-application-race-verify.mjs   # 既有：写入竞态
node tools/workflow-save-unit-verify.mjs         # 既有：工作流落库
node tools/line2line-verify.mjs                  # 既有：逐行应用
node tools/request-idempotency-unit-verify.mjs   # 新增：重试同请求/冲突不落库/迁移幂等
npm run build
```
**工时**：4–6 人日。

## A4 · 规划事务化（原子批量 + 单步撤销）

**现状**：大纲画布的数据模型在 `src/components/outline/canvas-model.js`（**UI 层目录下**），操作即改即存；"自动排布/批量移动/批量删除"没有事务边界，只能靠 UI 自己拼撤销。

**目标形态**（对齐催更姬 `planning.apply` + `planning.revert`）：
- 新增 `src/services/planning-tx.js`：`begin()` → 收集操作（`op/id/expectedRevision/value`）→ `commit()` 原子提交或整批失败；每次提交写一条事务记录（含前后快照摘要、`requestId`、作者原因）。
- 画布只对**三类高风险操作**先接事务：自动排布（`arrange`）、批量移动/归组、批量删除。单卡拖拽仍走原路（保证手感与回归面）。
- 事务撤销：按 `transactionId` 逆序回滚，且回滚前校验"其后没有对该批对象的后续修改"，有则拒绝并提示（对齐催更姬"布局撤销不覆盖后续内容修改"）。

**改动落点**：新增 `src/services/planning-tx.js`、`src/db/planning-tx-repo.js`；`db/database.js`（+1 表 `aplanningtx`）；`canvas-model.js` 的 `arrange`/`batch` 入口改为发事务；大纲工具条新增「撤销本批」。

**风险与回退**：画布是全应用回归最密的地方（`canvas-model-test`、`canvas-relations-test`、`outline-routing-verify`、`outline-scope-test` 等）→ 回退：事务层做成 **旁路订阅**（监听既有操作序列生成事务记录），第一阶段只"记录 + 可撤销一次"，不改原写入路径；确认稳定后再让写入走事务。

**验收命令**
```bash
node tools/canvas-model-test.mjs
node tools/canvas-relations-test.mjs
node tools/outline-routing-verify.mjs
node tools/outline-scope-test.mjs
node tools/planning-tx-unit-verify.mjs    # 新增：原子性/冲突拒绝/撤销顺序
npm run build
```
**工时**：8–12 人日。

## 分期与依赖

| 阶段 | 内容 | 依赖 | 累计工时 |
| --- | --- | --- | --- |
| P1 | A3（并发前置校验） | 无——先做它，因为后面所有写路径都受益 | 4–6 |
| P2 | A1（Skill 目录化） | 无 | 7–11 |
| P3 | A2（上下文检索化） | A1 的技能索引可复用为索引行来源之一 | 12–19 |
| P4 | A4（规划事务化） | A3 的 `requestId`/`revision` 是事务记录的前置 | 20–31 |

**为什么 A3 先行**：它是唯一能顺带降低"长章提取失败/聚合连坐"这类既有高优缺陷（见 `docs/恍然梦Agent能力评估.md` 四节）的基础设施，投入产出比最高。

## 非目标

- 不引入向量检索改造（工坊已有，反而应输出给催更姬）。
- 不改预设编译引擎的对外行为（作者已依赖）。
- 不动 Electron 主进程、不进 `server.mjs`（网页版数据独立性不改变）。
- 不做 MCP/子 Agent 接入——那是方案 B/C 的话题。
