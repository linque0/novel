# 06 · 决策建议

## 一、一句话建议

**先做方案 A 的 A3（并发前置校验），再依次 A1、A2、A4；方案 B 在 A 完成后作为收口开始；方案 C 只做"MVS 只读切片"用来验证宿主可行性，不做全量插件化。**

## 二、推荐顺序与理由

| 序 | 动作 | 理由 | 工时 |
| --- | --- | --- | --- |
| 1 | **A3 并发前置校验** | 唯一能顺带缓解既有高优缺陷（长章提取失败、聚合连坐、写入竞态）的基础设施；后续所有写路径都受益 | 4–6 |
| 2 | **A1 Skill 目录化** | 收益立刻可见（加方法论不改代码、常驻 token 下降），且是方案 C 工具面的雏形 | 3–5 |
| 3 | **A2 上下文检索化** | 直接决定长书可用性；但会改变作者可感知的注入内容，必须做开关灰度，所以放在 A1 之后 | 5–8 |
| 4 | **A4 规划事务化** | 价值高但回归面最大，最后做；先做"旁路记录 + 可撤销一次" | 8–12 |
| 5 | **方案 B（P1–P5）** | A3 完成后数据层已经半端口化，此时下沉阻力最小 | 29–46 |
| 6 | **方案 C 的 MVS** | 只在方案 B 的 P5（Node 适配器）跑通后才启动；目的不是上线，而是回答"宿主能不能用我们的数据" | 8–12 |

**如果只做一件事**：做 **A3**。它是唯一同时改善"正确性"与"后续可迁移性"的改动。

**如果只想要一个快速体感**：做 **A1**。它不碰写入路径，风险最低，一周内能看到作者侧变化。

## 三、翻转条件（什么情况下我该改主意）

| 当前建议 | 翻转条件 | 翻转后 |
| --- | --- | --- |
| A 优先于 B | 你打算**半年内**就把它装进 DSH 用 | 直接 B → C 的 MVS，A 的三项能力顺带在工具化时完成 |
| A 优先于 B | 你已放弃维护桌面版、只想保住一个形态 | 先定"保留哪个形态"，再选 A 或 C；摇摆期做 A 一定是浪费 |
| C 只做 MVS | 核实发现宿主提供 iframe/Web surface（约束 2 的解法二成立） | MVS 可以扩到"只读 + 真 UI"，因为 UI 宿主化成本骤降 |
| C 只做 MVS | 你接受"插件里没有恍然梦循环、完全交给宿主 agent" | 全量 C 仍不建议，但"工具面 + 预设资产"的 C-lite 可行（20 人日量级） |
| 不动向量检索 | 催更姬侧也要做 B3 | 那就把工坊的 `retrieval.js` 抽成共享包，两边用同一套 RRF |
| 不共享数据格式 | 你希望桌面版与 DSH 插件**写同一份作品** | 必须先定"作品目录契约"，这是独立的架构决策，不在 A/B/C 任何一份里 |

## 四、明确不做（及其理由）

1. **不做双向数据同步**。两个宿主同时写同一作品需要分布式锁与冲突合并，对本地优先的单人写作场景是无收益的复杂度。要共享就定"同一时刻只有一个可写宿主"。
2. **不为插件化把桌面版改造成 Web 应用**。Dexie 在本地优先软件里是优点；网页版数据独立已是既有事实（`server.mjs` 明示），不应被当成缺陷去修。
3. **不把催更姬的存储层搬进工坊**。工坊的 Dexie + 备份体系已经成立；文件存储只在方案 B 的 Node 适配器里出现。
4. **不在方案 A 阶段动 UI 栈或组件结构**。A 的价值就是"不碰 UI 也能拿到的能力"，一动 UI 就会变成方案 B/C 的活。
5. **不让两个 Agent 循环共存**。插件化后只保留宿主 `dsh-agent-loop`；恍然梦的循环不迁移。
6. **不追求「和催更姬功能对齐」**。它的强项（宿主继承、工具契约）与工坊的强项（预设引擎、写入安全、UI）本来就不该对齐，对齐只会两边都变差。

## 五、假设

**三套方案共同假设**
- 基线锁定催更姬 0.5.1 / 工坊 v1.1.3；不追上游主线。
- 你继续维护桌面版小说工坊（否则 A/B 的价值前提不成立）。
- 作者侧可接受"能力增强需要新开关"，即愿意为新模式付一次学习成本。

**方案 A 前置假设**
- 现有 `tools/*-verify.mjs` 脚本能在本机独立跑（本轮未执行，属 ⚠️ 未核实）。
- 作者已在用预设引擎；因此 A2 必须默认保持"全量"行为。

**方案 B 前置假设**
- 可以引入 workspace/子包结构（若坚持单包，B 退化为"目录内分层 + lint 守门"，工作量略降但边界更脆）。

**方案 C 前置假设**
- DSH 插件开发接口（`defineTool`/`registerRpcRoute`/`ctx.slots`）在目标版本稳定可用——催更姬的实践已证明可行，但工坊若要用更宽的 surface（iframe）则 ⚠️ 未核实。

## 六、下一步（等你点头再做）

1. 若选 A3：先补 `db.version` 迁移与 `airequests` 表的单测，再改 `application.js` 入口，最后跑 `writing-application-race-verify.mjs`。
2. 若想先验证 C 的可行性：只做 05 文档 §3 的 MVS，用备份 JSON 当数据源，一周内可得到"宿主能否读我们的书"的确定答案。
3. 若想先要体感：做 A1，一周内作者可在设置页里新增一条自定义方法论并让 AI 按需加载。
