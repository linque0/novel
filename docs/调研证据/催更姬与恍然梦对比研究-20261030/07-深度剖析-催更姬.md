# 07 · 深度剖析：催更姬的机制与工程设计

> 本文只写"代码里到底怎么做的"，每条都带 `文件:行`。目的是把可迁移的工程设计从实现细节里摘出来。

## 一、提示词装配：为前缀缓存而设计

`adapters/dsh/prompt.js` 挂在宿主的 `system-prompt/assemble` 钩子上，做的是一件很克制的事：

1. **只注入稳定段**。注释写明「omit changing metadata to keep this text stable」——persona 文本里不含时间戳、版本号、作品名，因此多轮之间这一段字节完全一致，天然命中 provider 的前缀缓存。
2. **只保留两个自有 section**：`cuigengji:writing`（persona）与 `cuigengji:preset`（作者已启用的写作要求）。每次装配先把 `OWN_NAMES` 里四个历史名字（writing/handoff/preset/novel）从结果里过滤掉再追加，等于**幂等重装**，不会重复堆叠。
3. **会话开关**：`guidance.enabled === false` 时不只是不注入，而是把四个 section 与 contexts 一起清掉（`prompt.js:14-16`），保证"关掉就真的没有残留"。
4. **故障不阻塞宿主**：捕获 `UPGRADE_REQUIRED` 后仍然放行，让宿主还能调维护工具与插件管理器（`prompt.js:19-24`）。这是"插件坏了不能让用户的 DSH 变砖"的工程取舍。
5. `interpolate: false`：persona 不做宿主侧变量插值，避免作者作品里出现双花括号变量时被误替换。

**可迁移点**：稳定段 + 幂等重装 + 开关即清空 + 故障降级，四件事都不依赖 DSH。

## 二、渐进披露：三层结构

| 层 | 机制 | 证据 |
| --- | --- | --- |
| 常驻层 | `persona` 文本（约 500 字），含**协作规则版本标记 `shared-canvas-v12`**，并写明"旧会话首次处理相关任务时，已加载的指南若没有这个版本标记，重新加载对应 Skill 一次" | `adapters/dsh/skills.js` 的 `persona` |
| 注册层 | 6 个 Skill 注册进宿主 `ctx.skills.register`；非 project 的 Skill 会把 project 的正文**追加**在自己后面，避免共享规则重复写六份 | `skills.js:16-25` |
| 按需层 | `readGuidance({section})` 在**调用时**从磁盘读 `SKILL.md`、剥掉 YAML frontmatter、返回 `resourceBase` 目录，让模型自行去读 `references/` | `adapters/dsh/guidance.js:5-12, 26-40` |

**为什么版本标记重要**：会话里可能已加载旧版 Skill 正文，模型不会自动重读。用一个字符串版本标记，把"缓存失效"变成模型自己可判断的条件，不需要宿主提供失效事件。

## 三、动作总线与 actor 边界

一切写操作都走 `store.dispatch(action, args, actor)`，actor 形如 `{kind:'human'|'agent', sessionId}`。`application/bindings/session.js` 在 dispatch 层（不是工具层）做策略：

- `binding.set`（切书）在会话运行中直接拒绝：报"会话正在运行，请停止后切换小说或章节"（`session.js:31`）。
- 整部作品的回收/恢复/永久删除**只允许 human**（`session.js:32`）。
- agent 的每次调用若不带 `novelId`，自动补当前焦点书；带了则视为**一次性借用**，不改变绑定（`session.js:33-37`）。
- `workingBooks` 记录本轮用过的所有书；回收时逐会话检查，命中则抛 `NOVEL_BUSY`（`session.js:40-46`）——**"你借过的书，别人不能删"**。
- `sessionKey = sha256(sessionId)`：会话 ID 落盘只存哈希。

**可迁移点**：权限与焦点策略写在 dispatch 层而不是散落在 UI/工具里，是"同一套规则服务作者面与 Agent 面"的前提。

## 四、版本与幂等：`cas` 一个函数管到底

```js
function cas(entity, args) {
  if (!Number.isSafeInteger(args.expectedRevision)) fail('REVISION_REQUIRED', '修改前请读取对象并提供 expectedRevision')
  if (entity.revision !== args.expectedRevision) fail('CONFLICT', '版本已变化，当前版本 ' + entity.revision)
  if (args.expectedHash !== undefined && args.expectedHash !== entity.contentHash) fail('CONFLICT', '正文内容哈希已变化')
}
```

（`application/store.js`）

- 缺版本号 → `REVISION_REQUIRED`（**强制先读后写**，不给盲写后门）；版本不符 → `CONFLICT`；内容 hash 可选叠加。
- `record()` 统一产出 `{id: uuid, revision: 1, createdAt, updatedAt}`；`touch()` 唯一负责 `revision++`。
- 每次正文写入都 push 一条 `versions[]`，字段含 `actor` 与 `reason`（`store.js` 的 `version()`）——**历史里记着是人改的还是 AI 改的、为什么改**。
- 根状态 `empty()` 自带 `requests: {}`，幂等请求结果就存在这里，与业务数据同一事务提交。

## 五、规划：所有写路径收敛到一个原子动作

`domain/planning/index.ts` 里，`planning.page.*`、`planning.group.*`、`planning.continue` **全部是 `planning.apply` 的语法糖**——它们拼一个 `operations` 数组再递归调用自己：

```ts
const result = planningAction(novel,'planning.apply',{...args,operations:[{op:'node.create',ref:'continuation',...},{op:'edge.create',...}]},actor)
```

这带来三个后果，全是对 Agent 友好的：

1. **原子性只有一处实现**：批次全成或全败；`ref` 允许同一批里先用临时名引用新建对象（`ref:'continuation'` 随后被 `edge.create` 的 `from` 使用），返回 `mapping` 把临时名映射成真 ID。
2. **乐观并发**：每个 op 自带 `expectedRevision`，批级另有 `expectedSequence`（画板单调序号）保护整批结构（见 `adapters/dsh/planning-schema.js` 的描述）。
3. **撤销有边界**：返回 `transactionId`，`planning.revert` 按事务回滚；`sequence` 让"我读到的是第几版结构"变成可校验事实。

分页与序号：`page()` 强制 `1<=limit<=200`、非法分页直接 `INVALID_INPUT`，返回 `{items,total,nextOffset}`（`domain/planning/index.ts`）。

## 六、存储：文件级事务

`infrastructure/persistence/file-transaction.ts` 不是"随手写 JSON"，而是一个小型 WAL：

- **持久化日志先行**：`transaction.pending.json` 在任何读者可见之前落盘（源码注释：A durable journal makes a batch recoverable before any reader can observe it, including after a process crash）。
- **原子替换**：写同目录 `.stage-<uuid>` → `fsync` → `rename` → 再对目录做一次 `fsync`（`barrier()`，Windows 上对不支持的错误码显式白名单放行）。
- **路径越界防护**：拒绝反斜杠、`..`、盘符冒号与任何逃出数据根的目标，异常统一 `CORRUPT_STORE`。
- 配套还有 `project-store.ts`/`project-layout.ts`/`project-directories.ts`/`upgrade-backup.ts`：布局版本、目录映射、升级快照各司其职。

**这是催更姬最值得学的一块**：IndexedDB 由浏览器保证事务，但**跨窗口、跨进程、崩溃恢复**没有等价物；文件事务给了它完整的恢复语义。

## 七、RPC 与 UI 边界

`adapters/dsh/rpc.js`：

- UI 只能调 `HUMAN_ACTIONS` 白名单里的 action（`if (!HUMAN_ACTIONS.includes(payload.action)) throw invalid(...)`）——**UI 不能借 RPC 绕过 Agent 面的限制，反之亦然**。
- `args.__libraryRoot` 与当前数据根不一致时抛 `LIBRARY_CHANGED`（提示"作品库已切换，旧页面的编辑已保留，请刷新后继续"）：**多标签页/多窗口下的陈旧页面检测**，而不是让旧页面写坏新库。
- 除白名单 action 外必须有 `sessionId`，否则 `SESSION_REQUIRED`。
- 所有库操作被 `libraries.use(fn)` 互斥包裹，切库期间其它请求排队。
- 错误统一经 `errorInfo(error)` 转成 `{ok:false,error}` 结构，前端不用猜错误形状。

## 八、它的缺口（不是实现缺陷，是定位使然）

1. **没有 token 预算概念**：工具定义、guidance 正文能塞多少全靠宿主；没有"预算不足就降级"的路径。
2. **没有冻结边界**：所有读取都是"当前版本"，没有"截至第 12 章的事实回放"——写第 20 章时，模型可能读到第 25 章之后的信息。
3. **没有结构化审稿协议**：`cuigengji-revise` 是行为规范（Skill 文本），不是可校验的数据契约。
4. **没有语义检索**，也没有跨对象的关系推理（只有 `edge.list/get` 的一跳邻接）。
