# 08 · 深度剖析：恍然梦的机制与工程设计

> 同样只写"代码里怎么做的"。这一侧的工程密度比外界印象高得多——它的短板不在实现质量，而在**边界**（自成一体的闭环）。

## 一、上下文冻结：在任何网络请求之前锁定世界

`novel-context.js` 的 `freezeContext()` 注释就是设计纲领：

> Freeze the source range before any credential or network await.

冻结出的对象包含：`workId`、`bookRevision`（全书资料 hash）、`chapterId/chapterTitle`、`sourceHash`、`order`（章节顺序）、`layoutHash`（章节↔卷映射指纹）、`allowedIds`（允许读的章节集合）、`asOfChapterId`（时间边界）、`scope`（book/chapter）、`selection`、`writingBoundary`（`{chapterId,end}`：写到哪个字符位置为止）、`anchorLength`。

三个细节值得抄：

- **抽取类任务**（`taskProfile(type).extraction`）的 `allowedIds` 是任务指定的章集合；普通写作是前缀集合（`chapters.slice(0, cutoff+1)`）——**同一份代码表达两种作用域**。
- `writingBoundary` 让"续写时后面还有已写内容"这种情形变成明确边界，而不是靠模型自觉。
- 选段必须属于关联章节，否则在冻结阶段就抛错（"选段不属于关联章节"），不把错误留到装配期。

## 二、四级装配 + 预算账本 + 覆盖报告

`assembleSlots()`（`novel-context.js`）是一条带账本的装配流水线：

- `remaining = clamp(adaptation.contextBudget || 6000, 256, 64000)`，由 `materialBudget(remaining)` 统一记账；每次 `add(slotName, label, items)` 都消耗预算。
- 槽位命名直接对齐酒馆：`worldInfoBefore`（设定）、`worldInfoAfter`（已发生事实/知识卡）、`characterFacts`、`workBrief`、`writingReference`。
- **它会把"为什么给这些"写进 report**："本轮范围事实覆盖：x/y 章；过期 z 章"、"知识检索：hybrid / lexical（原因）"之类。这份 report 随请求回到 UI——**发送范围对作者透明**，不是黑盒。
- 隐私模式不只是少给字段：`withoutQuotes()` 剥掉知识卡引文；人物卡的 `fields/content/relationships` 全部清空，并附注"作者设定是创作约束，阶段状态以正文证据为准；不将当前档案推断为历史事实"；`temporalStatus` 区分 `author-profile` 与正文回放。

## 三、预设编译：把酒馆语义真的执行了

`presets.js` 的 `compilePreset()` 关键设计：

1. **宏环境是完整一张表**：`user/char/group/charIfNotGroup/input/lastMessage/lastUserMessage/lastCharMessage/lastChatMessage/lastMessageId/lastSwipeId/currentSwipeId/maxPrompt/description/personality/scenario/persona/mesExamples/idle_duration……`，与 SillyTavern 同名同义。
2. **预算依赖宏的延后求值**：`firstIncludedMessageId` 依赖"裁完之后第一条是谁"，实现上先塞占位符 `__FIRST_INCLUDED_<id>__`，裁剪完成后再回填（源码注释：Resolve this budget-dependent macro after trimming, without evaluating stateful macros twice）。这是防"宏求值两次导致副作用"的老坑。
3. **块带语义标记**：每块是 `{role, content, blockId, protected, kind:'prompt'|'data'|'history'}`；`fitBlocks` 裁剪时优先保 `protected`——"数据块可裁、骨架不可裁"是可执行规则而非口头约定。
4. **产出可审计**：返回 `{warnings, report, sequence, injections}`——顺序、注入点、兼容性告警全部可见。

## 四、循环工程：预算先于请求

`dialogue.js` 的 `runDialogue()` 里有一串教科书级降级链：

| 情形 | 处理 | 后果 |
| --- | --- | --- |
| 工具定义 + 受保护块超预算 | 清空 `tools` 并 notice"完整请求预算不足以包含工具，使用普通对话；可将回复转为草稿" | 聊天还能用，不至于整轮失败 |
| 专用任务却没有工具 | 直接抛错"专用任务需要工具调用，请提高上下文预算或换用支持工具的模型" | 宁可失败也不产出没证据的正文 |
| 每轮 | `fitBlocks([...base, ...groups.flat()])` 重新裁剪，并把 `{round, tokens, toolDefinitionReserve, dropped}` 推进 `reports` | **每轮一份 token 账** |
| 阶段预算不足 | `charged + liability > rootRemaining` → 请求前抛"本阶段剩余批次预算不足，已在请求前暂停" | 不打"先烧后断"的仗 |
| 最后一轮 | `toolChoice: 'none'` | 强制终答，不让模型无限调工具 |
| provider 不支持 assistant prefill（400/422） | 撤掉 prefill，塞一条 `prefillFallback` 提示并 `round--` 重试 | 能力探测式降级 |
| 工具 schema 被 provider 拒（400/422） | 进入同构降级分支 | 兼容性兜底 |

再加 `roundLimit = task ? 24 : 6`、重复请求缓存、`checkAbort(signal)` 每轮与每个 delta 都查——**中断逐 token 生效**。

## 五、审稿协议：把"审稿"变成可校验的数据契约

`review-cycle.js` 是全项目最精细的一段，五个函数串成一条不可伪造的链：

| 函数 | 保证 |
| --- | --- |
| `freezeDraft(card)` | 冻结 `{id, revision, contentHash, text}` 并深度 immutable；正文上限 2,000,000 字符；hash 不符直接抛错 |
| `assertReviewCurrent(review, draft)` | 审稿结论绑定的源稿 `id+revision+contentHash` 必须与当前一致，否则"审稿来源已变化，请重新审稿" |
| `normalizeReview(data,draft,resolveEvidence)` | 条目 ≤200；`quote` 必须**唯一定位**（给了 start 就逐字核对，没给就要求全书只出现一次）；每条 `evidence` 会被 `resolveEvidence` 反查并标 `verified/unverified`；问题 id 去重，缺 id 时用 `category+problem+quote` 的 FNV hash 生成确定性 id |
| `confirmReview(review,draft,decisions,authorGuidance)` | 作者决策只接受 `apply/ignore/defer`，id 必须属于原审稿；只有 `apply` 的条目进修稿 |
| `normalizeRecheck(data,review,revisedDraft)` | 复核必须**恰好覆盖全部原问题、不许多不许漏**；草稿 `revision` 必须前进；`resolved` 若 `quote` 定位失败会被**降级为 `unresolved`** |

**意义**：它把"AI 说改好了"变成"你能指给我看改在哪一行，且那一行确实在原稿的当前位置"。多数写作 Agent 没有这个。

## 六、写入闸门：一篇提案要过十道关

`application.js` 的 `proposalGuard()` 实际检查顺序：

1. 工作流阶段材料不能直接应用；2. 专用任务的动作白名单（`taskApplyActions`）；3. `workId` 归属；4. `layoutHash`（章节顺序/所属卷）；5. 逐个 `sourceVersions` 的实体 hash；6. `bookRevision` 全书 hash；7. 提案完整性 `complete !== false`；8. 是否已应用（`appliedActions`）；9. 目标是否被删除；10. **目标是否被其它窗口锁定**（`isPopped`）；11. 目标 `sourceHash`。

`locateEditorPatch()` 再补三道：编辑器正文必须**唯一匹配**候选源稿片段（否则"无法唯一定位改稿片段"）、整章模式要求 `normalizeText(getHTML()) === original`、并探测 `protectedMark`（`dl/link/note/annotation` 标记）——**改稿不允许破坏双链、批注与富文本标记**。

`applyProposal()` 再加两道：`applying` Set 防重复点击；工作流候选在采纳瞬间重新 `freezeDraft` 比对 `contentHash+revision`，检测"作者在采纳过程中改了候选"。

## 七、多窗口协作

`prepare-dialogue.js` 的 `requestMainPreview()`：拆窗里的 AI 面板通过 `window.native.appBroadcast` 发 `ai-preview-request`，主窗口算出预览后回 `ai-preview-response`，15 秒超时、`requestId` 对号入座——**跨窗口走请求/响应协议，不共享内存**。

## 八、它的缺口（结构性的，不是修 bug 能解决）

1. **闭环**：无 MCP、无外部工具、无子 Agent；模型输出里出现 `subagent/mcp__/tool_calls` 字样会被 `stage-config.js:22` 的 `unsafeText` 过滤掉——**自我设限**，换来的是可控。
2. **无外部可编排性**：所有能力只在自家 UI 里可调用，编辑器外、其它 Agent 无法复用。
3. **循环无规划**：`roundLimit` 是硬上限，"给定目标自主分解"不存在；22 类任务是模板，不是计划。
4. **工作记忆不持久**：会话历史在内存，刷新即失。
5. **提示词不稳定**：每轮 `fitBlocks` 都会改变消息内容与裁剪结果，**前缀缓存命中率天然不高**（与催更姬的稳定段策略正好相反）。
