## A 簇：上下文与预算

### C1 稳定提示词段 + 版本标记（工坊 ← 催更姬）

- **工坊的缺口**：`runDialogue` 每轮 `fitBlocks` 重算消息，裁剪结果随轮变化，system 段不稳定 → 前缀缓存命中率低（`dialogue.js:285-300`）。
- **催更姬做法**：只注入稳定 persona，注释明确"omit changing metadata to keep this text stable"，且**幂等重装**（先滤掉自有 section 再追加）（`adapters/dsh/prompt.js`）。
- **合成接口**：预设编译产物增加 `stable: boolean` 标记；`fitBlocks` 对 `stable` 块**永不裁剪、永不重排**，且不允许插入动态内容；动态内容一律进 `kind:'data'` 块。
- **验收**：同一会话连续 3 轮，第 1 轮与第 3 轮的 `messages[0].content` 字节相等。

### C2 预算前置拒绝（催更姬 ← 工坊）

- **催更姬的缺口**：无 token 预算概念，塞多少由宿主决定。
- **工坊做法**：`liability = fitted.tokens.used + toolReserve + maxTokens`；`charged + liability > rootRemaining` 时**在请求前**抛"本阶段剩余批次预算不足，已在请求前暂停"（`dialogue.js`）。
- **合成接口**：工具层增加可选 `budget: {remaining}` 上下文；超预算时工具返回结构化 `{ error:'BUDGET', required, remaining }`，而不是让宿主先失败。
- **价值**：催更姬的 `concept` 工具（`graph.get` 全文）最容易被大对象撑爆，前置拒绝比事后报错便宜得多。

### C3 工具预算探测与降级（催更姬 ← 工坊）

- **催更姬的缺口**：66 个 action 的 schema 常驻，没有"塞不下就降级"的路径。
- **工坊做法**：`toolCost + protectedBlocks > budget - maxTokens - 128` → 清空工具并 notice（`dialogue.js` 开头）；任务模式无工具则硬失败。
- **合成接口**：工具注册时声明 `tier: 'core'|'extended'`；预算不足时只保留 `core`（对应 project/context 的核心读），并在回复里附一行"扩展工具本轮不可用"。
- **注意**：催更姬的工具是**宿主注入**的，插件不能删宿主工具，只能在自己注册的工具上分层——因此这条要落在 `defineTool` 的注册策略上。

### C4 索引式按需装配 + 覆盖报告（双向）

- **工坊的缺口**：装配是全量拼装 + 预算裁剪，**被裁掉的内容模型不知道自己被裁了**（`assembleSlots` 只把裁剪写进 `report` 给作者看，没给模型）。
- **催更姬做法**：正文/设定/规划一律"先摘要索引、再按需读全文"，`planning.get` 还带 `resources:{items,total,nextOffset}` 的有限摘要与分页（`docs/planning-board.md`）。
- **工坊已有的好东西反向输出**：`report` 的"本轮范围事实覆盖：x/y 章；过期 z 章"这种**覆盖率陈述**，催更姬没有对等物。
- **合成接口**：装配产出一段固定的 transport notice：
  ```
  【本轮材料】已注入：作品概况、当前章锚点、知识卡 12 条（覆盖 8/12 章）；折叠：设定 34 条、人物 9 位。
  需要时用 search_book / read_document / graph.get 展开；折叠不等于不存在。
  ```
- **判据**：同一问题的回答质量不降，但首轮 token 下降 ≥30%。

## B 簇：一致性与并发

### C5 `requestId` 幂等（工坊 ← 催更姬）

- **工坊的缺口**：网络重试或用户重复点击会重复生成/重复落库；只有 `applying` Set 这种内存级防重（`application.js`）。
- **催更姬做法**：`requestId` 落盘在 `runtime/requests/`，同请求原样重试返回上次结果（`docs/architecture.md`；`store.js` 的 `empty()` 含 `requests:{}`）。
- **合成接口**：`applyProposal(work, card, { requestId })`；命中则返回 `{ replayed: true, auditId }` 而不重复执行。

### C6 `cas` 双校验（工坊 ← 催更姬）

- **工坊现状**：`proposalGuard` 只用 hash 事后比对（`entityHash`/`sourceHash`/`bookRevision`），**冲突只能发现、不能预防**。
- **催更姬做法**：`cas(entity,args)` 强制 `expectedRevision`（缺则 `REVISION_REQUIRED`）+ 可选 `expectedHash`，`touch()` 独占 `revision++`。
- **合成接口**：两者并存——`revision` 管"别人动过"，`hash` 管"内容确实一致"，都不过就 `CONFLICT` 并把 `{currentRevision, currentHash}` 返回给调用方重读合并。
- **注意**：工坊的 hash 是**内容级**，催更姬的 revision 是**对象级**，两者缺一不可（内容相同但被重存过，revision 也会前进）。

### C7 单一原子写路径（工坊 ← 催更姬）

- **工坊现状**：写入口分散——`applyProposal`（提案）、`applyWorkflow`（工作流）、`undoApplication`（撤销）、画布各操作各走一条。
- **催更姬做法**：`planning.page.*`/`planning.group.*`/`planning.continue` **全部是 `planning.apply` 的糖**，`ref` 支持批内临时引用，返回 `{mapping, sequence, transactionId}`。
- **合成接口**：工坊侧定义 `applyBatch(ops, {requestId})` 作为唯一写入口，现有 `applyProposal` 退化为"把一张卡片翻译成 ops 的适配器"。
- **收益**：撤销、审计、幂等、冲突检测只需实现一次（现在是四套各写一遍）。

### C8 文件级事务与崩溃恢复（催更姬 ← 工坊）

- **催更姬已有**：journal 先行 + stage/fsync/rename + 目录 barrier + 路径越界防护（`file-transaction.ts`）。
- **工坊能给什么**：`writingBoundary`/`frozen.sourceVersions` 这套"这次写入基于哪些版本"的溯源，催更姬的事务只保证原子，不记录"依据"。
- **合成方向**：催更姬的事务日志增加 `basis: [{table,id,revision}]` 字段——崩溃恢复后可以判断"恢复出来的状态是否仍与作者当前版本一致"。

### C9 会话焦点 vs 多窗口锁（互学）

- **催更姬**：`session policy` 管焦点（`binding.set` 运行中拒绝、`workingBooks` 保护、`NOVEL_BUSY`），但**没有"某个对象正被某窗口编辑"的概念**。
- **工坊**：`isPopped(work, type, id)` 做目标窗口锁（`proposalGuard` 第 10 道），但**没有会话级焦点**（作品由 UI 当前选中决定）。
- **合成接口**：两侧都需要两层锁——`session → book`（焦点）与 `window → entity`（编辑权）。催更姬补后者，工坊补前者。

### C10 多窗口目标锁（催更姬 ← 工坊）

- **催更姬现状**：多标签页只有 `__libraryRoot` 的**整库陈旧检测**（`LIBRARY_CHANGED`），粒度太粗：同一本书两个标签页同时改不同章是允许的，改同一章会互相覆盖（靠 revision 冲突发现，但发现得晚）。
- **工坊做法**：`isPopped` 在写入前直接拒绝"目标被其他窗口锁定，请到对应窗口操作"。
- **合成接口**：`{ targetKind, targetId, sessionId }` 的软锁 + TTL；与 `expectedRevision` 并存（软锁防冲突，revision 兜底）。

## C 簇：质量闭环

### C11 结构化审稿协议（催更姬 ← 工坊）

- **催更姬现状**：`cuigengji-revise`/SKILL.md 是**行为规范**，模型说"改好了"没有数据契约兜底。
- **工坊做法**：`normalizeReview` 要求每条问题给出可在源稿**唯一定位**的 `quote`，每条 `evidence` 反查来源标 `verified/unverified`，id 去重且确定性生成（`review-cycle.js`）。
- **合成接口**（可直接抄形状，不抄实现）：
  ```ts
  type Finding = {
    id: string                 // 缺省时由 category+problem+quote 派生
    severity: 'error'|'warning'|'suggestion'
    quote: string              // 必须在源正文中唯一出现
    start?: number
    evidence?: { sourceType:'chapter'|'setting'|'planning'; sourceId:string; quote:string; verified:boolean }[]
  }
  ```
- **落点**：插件新增 `cuigengji_review` 工具（`submit_review`-style 输出契约），把"审稿"从 Skill 文本升级为可校验数据。

### C12 复核全覆盖 + 定位失败降级（催更姬 ← 工坊）

- **工坊做法**：`normalizeRecheck` 要求复核**恰好覆盖全部原问题、不许多不许漏**，草稿 revision 必须前进，`resolved` 若 `quote` 定位失败**降级为 `unresolved`**。
- **为什么重要**：这是防"模型假装改好了"的最有效机制——它无法通过删改原句来伪造 resolved。
- **依赖**：需先有 C11 的 findings 身份（确定性 id），否则无法对齐"原问题"。

### C13 冻结边界（催更姬 ← 工坊）

- **催更姬缺口**：读到的永远是当前版本，写第 20 章时能看到第 25 章的内容——**未来信息泄漏**，长书里这是最隐蔽的一致性杀手。
- **工坊做法**：`freezeContext` 产出 `asOfChapterId` + `allowedIds` + `writingBoundary{chapterId,end}`，`executeTool` 在入口处强制裁剪（`if (env.asOfChapterId) ... allowed`，`tools.js:190-200`）。
- **合成接口**：插件工具增加可选 `asOf: { chapterId, end? }`；`chapter.get`/`graph.get`/`planning.get` 在 `asOf` 下只返回截至该章的内容，并在返回里标注 `scope:'asOf:12'`。
- **注意**：这需要存储层能"按章序回放"，催更姬的 `settings/history/` 已按次留档，缺的是**按章序查询**的索引。

## D 簇：驾驶层与检索

### C14 Skill 渐进披露 + 规则版本标记（工坊 ← 催更姬）

- **工坊现状**：`builtin-writing-skills.js` 是 4 段固定阶段文本，随阶段整段注入（`memory-stage.js:12`），新增方法论要改代码。
- **催更姬做法**：三层（persona 常驻 / Skill 注册 / `guidance` 按需读盘 + `resourceBase` 读 references），并用 `shared-canvas-v12` 版本标记解决"会话里已加载旧文"的失效问题。
- **合成接口**：工坊新增 `list_skills`/`load_skill` 两个只读工具 + `aiskills` 表；阶段默认技能仍 inline（不改变现有行为），额外方法论按需加载。
- **已量化的体积**（本轮实测）：6 个 `SKILL.md` 合计 **43,013 字节**（含 `references/` 共 54,825 字节），按 UTF-8 中文约 3 字节/字折算 ≈ **9.5k token**；其中 `cuigengji-project` 单个 12,340 字节（≈2.7k token）。
- **一个反直觉的实测发现**：`skills.js` 为了去重，把 project 的正文**追加**到 write/plan/memory/revise 四个 Skill 后面——于是按需加载任一技能实际付的是 **自己的 + project 的**（如 `cuigengji-write` ≈ 5,183 + 12,340 ≈ 17.5KB ≈ 3.9k token）。**去重省的是维护成本，不是 token**。
- **对工坊 A1 的启示**：技能目录必须做**共享段**（只加载一次、按需引用），否则"渐进披露"在长会话里会退化成"每次都重读项目指南"。

### C15 预设编译（催更姬 ← 工坊）

- **催更姬现状**：导入 Chat-Completion/PromptManager 预设后**只保留文本**，明确不执行宏、装填深度、触发条件（`docs/presets.md`「酒馆格式的边界」）。
- **工坊做法**：完整宏表 + `firstIncludedMessageId` 占位符延后求值 + `protected/data` 块语义 + `fitBlocks` 预算裁剪 + `injection_position`/`depth`（`presets.js`、`regex.js` 的 `depth`）。
- **合成接口**：插件侧 `domain/preset/index.js` 扩为编译器；宿主没有"消息级装填"的位置，因此**只承诺三件事**：宏展开、块顺序与优先级、预算裁剪。触发条件/角色语义不承诺（避免过度承诺）。
- **风险**：宿主 system prompt 是分段拼接的（`prompt.js` 的 `sections`），预设块只能落在 `cuigengji:preset` 这一个 section 内，**无法插入对话历史中间**——这是插件形态的硬边界。

### C16 语义检索（催更姬 ← 工坊）

- **催更姬**：只有文本/摘要检索（`grep embed|vector` 零命中）。
- **工坊**：`kbQuery` 关键词 + 向量 + `fuseRanks` RRF，向量不可用时降级 lexical 并在 report 里说明原因（`retrieval.js:17,52-68`）。
- **合成接口**：插件 `graph.list`/`chapter.search` 增加 `mode:'lexical'|'hybrid'`；缺少嵌入配置时**自动降级并告知**，不静默失败。
- **依赖**：嵌入模型来自宿主配置，插件不应自己管密钥。

### C17 `written` 的正文证据（互学）

- **催更姬已有**：规划节点的 `written` 状态**必须**带 `chapterRefs:[{chapterId,revision}]`，否则不能算实现（`planning-schema.js` 的 `chapterRefs` 描述；`docs/planning-board.md`）。
- **工坊缺口**：大纲节点/事件没有"已被哪一版正文落实"的引用模型；`outline.plan` 与正文之间只有松耦合。
- **合成方向**：工坊画布节点增加 `chapterRefs`，并纳入 `proposalGuard` 的 hash 校验——**"计划完成"从此有据可查**。

## 落地优先级（结合施工成本）

| 优先 | 互补点 | 理由 |
| --- | --- | --- |
| P0 | C5 + C6 + C7 | 一次重构同时拿到幂等、前置校验、单一写路径；后续全部受益 |
| P1 | C11 + C12 | 纯增量（新增工具与契约），不改现有写入路径 |
| P1 | C14 | 不碰写入，作者侧可见，风险最低 |
| P2 | C1 + C4 | 上下文与缓存优化，需要跟预设引擎的既有行为对齐 |
| P2 | C16 | 依赖宿主模型配置，先做可降级的 lexical/hybrid 开关 |
| P3 | C13 + C17 | 需要存储层支持按章序回放与正文引用索引 |
| P3 | C10 + C9 | 跨宿主/跨窗口锁，等 B 方案的双宿主问题定型后再做 |
| P4 | C15 | 受插件形态硬边界限制（只能落一个 section），收益有上限 |
| P4 | C2 + C3 | 等宿主提供预算/工具分层接口，插件单侧做不到 |
