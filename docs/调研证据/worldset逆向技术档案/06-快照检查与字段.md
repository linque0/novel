# A. 快照版本历史

## A1. 触发（三条路径）

| trigger | 触发方式 | 备注默认值 |
| --- | --- | --- |
| `auto` | `updateEntry(id, patch, note)` **第三参数必须是字符串**，且（1）canonical 哈希变化（2）距该条目最新快照 `≥ minIntervalMin` 分钟（3）`versionCfg.enabled !== false` | `保存修改`（由调用方传入，如「编辑条目」） |
| `manual` | `addSnapshot(entryId, note)`，UI 按钮 | `手动快照` |
| `restore` | `restoreSnapshot` 恢复前自动记录 | `恢复前自动快照` |

关键坑：
- **1.5s 防抖的正文自动保存不传 note → 不产生快照**；只有显式「保存」才产生。
- 快照载荷取自**编辑前**的条目状态。
- `addSnapshot` 在关闭历史时返回 false 并提示「修改历史已在项目设置中关闭」；`restoreSnapshot` **不检查 enabled、也不受节流限制**。

## A2. 记录形状与哈希

```js
payload(e) = { name, alias:"" , summary:"", content:"", status, importance, visibility,
               tags:[...], fields:{...}, parentId:null, fieldTemplateId, categoryId, notes:"" }   // 14 字段

hash  = FNV-1a 32 位（对 canonical JSON：对象键递归排序） → 8 位小写 hex
bytes = canonical JSON 的 UTF-8 字节数（TextEncoder）

record = { id:"ver_*", entryId, trigger, note（经 sanitize：空白折叠/trim/截 60 字，空则回退默认名）,
           createdAt, contentSnapshot, summarySnapshot,        // 旧格式扁平兼容
           data: payload, hash, bytes, ...(media ? {media:{coverUrl,coverFocus,images}} : {}),
           starred }
```
`isLegacy(snapshot) = !snapshot.data` → 读取时回退 `{content: contentSnapshot, summary: summarySnapshot}`，恢复时只回滚这两个字段（其余不动），列表标签附 `· 旧格式（仅正文与摘要）`。

## A3. 配置与限额

```js
默认  { enabled:true, maxPerEntry:20, minIntervalMin:10, maxBytesPerProject:50MB(0x3200000), includeMedia:false }
范围  maxPerEntry [5,100] · minIntervalMin [1,120] · maxBytesPerProject [5MB, 500MB]
免费档 maxPerEntry 压到 5 且 includeMedia 强制 false（门控 version_history_full）
```
设置页写入的是**解析后的完整 cfg**（并非降级后的值）；降级只在读取渲染时应用。

## A4. 清理算法（每次新增/恢复后执行）

```
按 entryId 分组，逐条独立（与项目边界无关）：
  保留 = 最新一条（恒定保留） + 全部星标 + 最新的 (maxPerEntry - 星标数 - 1) 条非星标
体积检查：Σ bytes（缺失则重算 canonical 长度）
  若 > maxBytesPerProject：在「非星标 且 属于本项目条目集」中**从最旧开始**删除直到达标
  星标永不被删
```
无「立即清理」入口，只有「清空全部历史」（确认文案明确「条目本身的内容不受影响」）。

## A5. 恢复语义

```
恢复键 = data 的 14 个字段（与对话框文案「名称、摘要、档案字段、标签等」一致）
流程   = 先写一条 trigger:"restore" 的当前状态快照 → 再把 data 合并回 entry（updatedAt = now）
        → 跑一次清理（于是很旧的恢复可能挤掉别的版本）
撤销   = 恢复那条 restore 快照即可（toast「恢复前的状态也存进了修改历史，可随时撤销」）
```

## A6. 逐字段 diff

固定键序与标签：`name 名称 / alias 别名 / summary 摘要 / content 正文 / status 状态 / importance 重要度 / visibility 可见性 / tags 标签 / fields 档案字段 / parentId 上级区域 / fieldTemplateId 模板组 / categoryId 分类 / notes 备注`。
比较方式：`fields` 用 canonical JSON，`tags` 用 `join("、")`，其余 `String(v ?? "")`；相同则跳过。
`kind = 前有后无 ? removed : 前无后有 ? added : changed`；文案映射 `added→新增(绿) / removed→清空(红) / changed→修改(琥珀)`。文本截断 120 字；`fields` 渲染为 `key=value` 以 `；` 连接，值截断 24 字（空显示 `（空）`）。脚注说明「正文按去除标签后的文本做粗粒度比较」。

## A7. UI

- 条目详情页可折叠面板「修改历史 · N」，列表先显示 **8** 条，再「查看全部 N 个版本 →」打开 560px 弹窗；每行：星标 / 查看 / 对比 / 恢复 / 删除，点击备注可内联改名（Enter 保存、Esc 取消、清空回默认名）。
- 行元信息：`{相对时间}{ · 大小}{ · 旧格式（仅正文与摘要）}`；触发类型渲染 `自动/手动/恢复`。
- 底部说明：`每个条目最多保留 {maxPerEntry} 个版本，全项目上限 {MB} MB；星标版本不会被自动清理。`（免费档追加 `免费版上限 5 个版本、不含封面与图集（PRO 可自定义）`）
- 星标 toast：`已星标（该版本不会被自动清理）`。恢复确认标题 `恢复到这个版本？`。

# B. 设定检查引擎（`m18367`）

## B1. 单条完整度评分（0–100）

| 项 | 满分 | 条件 |
| --- | --- | --- |
| 摘要 | 10 | `summary.trim().length > 0`，否则记「缺少摘要」 |
| 正文 | 20 | **去标签后**文本长度 ≥100 得 20；>0 得 8；否则记「正文尚未撰写」 |
| 标签 | 10 | `tags.length ≥ 1`，否则「尚未添加标签」 |
| 关联 | 20 | 度数 ≥1（relations 里任一端），否则「尚未建立任何关联条目」 |
| 字段 | 40 | 有可见字段集时 `round(已填/总数*40)`；无字段集时按正文长度给 40 或 16 |

可见字段集 = 该条目模板组字段 **减去** `entry.mutedFields`。缺失字段明细最多列 4 个，其余汇总为「另有 N 个字段未填写」。
`积分上限 100`。

## B2. 项目级指标

```js
{ entryCount,
  avgCompleteness = round(Σ 单条评分 / 条数),
  relationCount,
  relationDensity = round(关系数/条数*10)/10,
  orphanCount     = 度数为 0 的条目数,
  incompleteCount = 单条评分 < 70 的条目数,
  conflictCount   = 非 info 级别的 issue 数 }
```
仪表盘展示：`设定完整度 {avg}%`、`关联密度 {density} / 条目`（进度条 = `min(100, 20*density)`，即密度 5 满格）、`待确认设定 {incompleteCount} 项`、`冲突提醒 {conflictCount} 项`、`孤立条目 {orphanCount} 个`（>3 告警）。侧栏徽标 = 非 info 的 issue 数。

## B3. issue 形状与级别

```js
{ level:"error"|"warn"|"info", kind, title, detail?, hint?, entryIds:[…] }
id = kind + "_" + entryIds.join("_")
```
只有 `info` 视为「非必须处理」；`error`/`warn` 计入冲突提醒与徽标。**无「忽略/已处理」状态，无持久化** —— 修数据或加豁免标签才会消失。

## B4. 规则清单（17 条，含依赖字段）

| # | kind | 级别 | 条件（依赖） | 标题模板 | 豁免 |
| --- | --- | --- | --- | --- | --- |
| 1 | `dead_active` | warn | 人物用途分类 & `fields.char_state ∈ {死亡,封印,失踪}` & 存在 `relationType==="参与"` 的关系 & 无豁免标签 | `「{name}」状态为{char_state}，但仍关联 {N} 个事件` | 标签 `复活/亡灵/回忆/数据体` |
| 2 | `double_allegiance` | **error** | 人物通过 `效忠于`/`隶属于` 指向 ≥2 个互相敌对的势力/组织 | `「{name}」同时效忠于互相敌对的「{A}」与「{B}」` | 标签 `卧底` |
| 3 | `contested` | warn | 地点被 ≥2 个互相敌对来源 `统治`/`控制` | `「{name}」同时被敌对势力「{A}」与「{B}」控制` | 标签 `争夺中` |
| 4 | `timeline_order` | error | 关系 `前置于` 但 `src.start_year >= tgt.start_year` | `「{src}」应早于「{tgt}」，但记录的发生时间矛盾` | — |
| 5 | `causality` | warn | 关系 `起因于` 但 `src.start_year > tgt.start_year` | `「{src}」起因于「{tgt}」，但二者时间顺序可疑` | 标记待考据 |
| 6 | `lineage_cycle` / `evolution_cycle` | error | 谱系/演化图 DFS 三色标记发现环 | `{亲缘\|演化}关系存在循环：{A} → {B} → {A}` | — |
| 7 | `lineage_dup` | info | 同一对之间 ≥2 条谱系边（spouse/sibling 去方向，其余按方向） | `「{A}」与「{B}」之间有 {n} 条重复的{kindLabel}关系` | — |
| 8 | `lineage_parents_count` | warn | `parent` 类父母 >2 | `「{x}」有 {n} 位生身父母` | 改为收养 |
| 9 | `lineage_birth_adopt` | info | 同一父母同时是 parent 与 adoptive | `「{x}」与 {ps} 之间同时存在生身与收养关系` | — |
| 10 | `lineage_incest` | warn | spouse 双方为直系祖先，或共享生身父母 | `「{A}」与「{B}」是配偶，但{A}是{B}的直系长辈` | — |
| 11 | `lineage_sibling_conflict` | warn | sibling 同时存在亲子或配偶关系 | `「{A}」与「{B}」既是手足，又存在{亲子\|配偶}关系` | — |
| 12 | `lineage_sibling_mergeable` | info | sibling 且有已登记的共同父母（可由推导得出） | `「{A}」与「{B}」的手足关系可由共同父母（{ps}）自动推导` | — |
| 13 | `orphan` | info | 项目内度数为 0 | `「{name}」尚未与任何条目建立关联` | — |
| 14 | `no_tag` | info | `tags.length === 0` | `「{name}」没有标签` | — |
| 15 | `incomplete` | info | 评分 < 50 且 `status !== "deprecated"` | `「{name}」完整度仅 {score}%` | detail = 前 3 条缺失项 |
| 16 | `manual` | info | `status ∈ {verify, conflict}` | `「{name}」处于{待考据\|存在冲突}状态` | — |
| 17 | （规则 1 的死因探测）| — | 「敌对」判定：两条目之间存在 `relationType` **或** `reverseRelationType` ∈ `{敌对, 背叛}` 的关系（忽略方向） | — | — |

注意：规则 1/4/5 依赖固定字段键 `char_state` / `start_year` 与固定关系名 —— 这正是这几个键被列为**改名保护键**的原因。规则 1 只匹配 `relationType==="参与"`（若语义写在 `reverseRelationType` 上会漏判）。

## B5. 检查页结构

- 顶部三块指标：`矛盾项 / 存疑项 / 提示项`（error/warn/info 计数，色 `--danger/--warn/--info`）。
- **按 kind 重分组**（不是按级别），固定顺序：`潜在冲突与矛盾`（errors+warns 去掉 lineage_*/evolution_*）· `谱系一致性` · `孤立条目` · `缺失标签` · `未补全设定` · `待人工确认`。
- issue 卡：级别列（圆点+标签，52px）· 标题（13px）· detail（12px `--fg-muted`）· 可选「处理建议：{hint}」（`--accent`）· 条目 chips（点击跳条目页，右键出条目菜单，未知 id 显示「未知条目」）。
- 无逐条动作按钮；「跳转 + 补标签」是唯一解法。底部有「前往条目库」→ `?incomplete=1`。
- 空态：`设定检查无待处理项`。

# C. 分类与字段模板（含改名迁移）

## C1. 字段与模板组

```js
Field         = { key, label, type:"text"|"textarea"|"select", options?:string[], placeholder? }
TemplateGroup = { id, name, fields:[Field] }        // id "__default" = 内置默认组
```
模板组解析链：
```js
xB(cat)           = cat.fieldTemplates（非空） || [{ id:"__default", name:"默认字段", fields: cat.fieldTemplate||[] }]
T([...祖先, 自身]) = 按 id 合并组，按字段 key 覆盖（后者胜）；空字段组跳过；"__default"/空名不覆盖
B1(cat, 祖先)      = 有祖先链 ? T([...祖先, 自身]) : xB(cat)
wN(cat, entry)    = 组 by entry.fieldTemplateId，回退 [0]
In(cat, entry)    = wN().fields 减去 entry.mutedFields
Xr(..., {hideEmpty}) = In 再按「值非空」过滤（只读展示用）
aL(cat)           = 全部组字段 key 的并集（导出/搜索用）
```
**子分类自动继承父分类的用途与字段模板**。

## C2. 单条目「此字段不适用」(`mutedFields`)

条目编辑器每个字段右侧有「本条目不适用」勾选 → 该 key 进 `mutedFields`。效果：详情页/阅读导出隐藏；**从完整度分母中剔除**；值保留（取消勾选即恢复）。

## C3. 改名迁移（三步：校验 → 计划 → 事务）

**校验**（失焦时）：
```
空 → 「字段名称不能为空」
>60 字 → 「字段名称过长（最多 60 个字）」
∈ {__proto__, constructor, prototype} → 「该名称不可用，请换一个」
找不到该字段 → 「找不到该字段（可能已被删除，请关闭后重新打开）」
label 未变 → { ok:true, keyPreserved:true, changed:false }
本组内 label/key 冲突 → 「「X」已被本模板组里的另一个字段使用，请换一个名称」
命中改名保护键 OR 仅改显示名 → { newKey: oldKey, keyPreserved:true }   // 只改 label
```
`keyPreserved` 时 toast `已修改显示名` + `该字段的键名由其他功能使用，保持不变；条目里已填的值无需迁移。`

**计划**（`sn`）：
```js
renames = 过滤掉 oldKey===newKey 的项
按 groupId 分组 renames
对每个条目：
  用 wN(该条目的分类, 该条目) 解析出**该条目实际使用的模板组**（尊重 fieldTemplateId）
  取该组的 renames；对每项：
    仅当**旧 key 是自有属性**且**新 key 不存在**时才搬值（绝不覆盖已有值）
  有改动的条目进入待更新集
返回 { entries, count }
```

**事务**（Dexie `rw` over `categories + entries`）：
```js
categories.put({...cat, ...patch, id})
entries.bulkPut(重键后的条目)
返回 count
```
- 保存前用内存态算一遍 count，弹确认：`重命名字段` / `将更新 {count} 个条目里该字段的值名称（内容不变）——条目可在版本历史里回滚。` / 确认按钮 `改名并更新`。
- 成功 toast：`分类已更新` + `字段名已更新，并同步迁移了 {n} 个条目的值`（`count===0` 时 `字段名已更新（没有条目存过这个字段的值）`）。
- 失败 toast：`保存失败` + `字段改名没有完成，数据保持不变。`（对话框不关闭）。
- **迁移本身不写快照**，靠条目自身的版本历史回滚。
- 保存时：丢弃 0 字段的模板组；全空则保留一个空 `__default`；只剩一组时隐藏模板选择器；删除组不删条目里的值（重新加回组即恢复）。

## C4. 移植备忘

- 检查引擎的价值在**形态**（`{level, kind, title, detail, hint, entryIds}` + 分组 + 项目级指标 + 豁免标签），17 条规则里大半依赖原站特有的结构化字段与固定关系名。移植到 novel-studio 时应**重写规则集**，只保留 4 条与结构无关的：`orphan` / `no_tag` / `incomplete` / 悬空引用（novel-studio 有 `olBroken` 与双链）。
- 快照系统可**直接泛化** novel-studio 现有 `revisions`（当前仅章节、每实体 30 条、5 分钟节流）：补上 canonical 哈希去重、`trigger` 三态、星标保护、字节上限、恢复前自动快照、逐字段 diff —— 这六项是增量价值所在。
- `fields`（扁平字符串表）+ `select` 选项是「档案字段」最省的实现；novel-studio 的人物已有 `fields{}` 先例，可沿用同一形态扩展到设定节点。
