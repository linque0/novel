## 目标

把三份数据集（`agent`、`jfix`、`小说工坊`）连同 dev 当前实时数据，按**标题归并成一份**，落在 dev 上；同名验证书**内容多的那份胜出**；完成并验证后**删掉 agent/jfix，只留 dev**；并让 5 个硬编码隔离 profile 的验收脚本改为跑在 dev 上。

## 关键事实（已核实）

- 三份数据集都是 `IndexedDB/http_127.0.0.1_5173.indexeddb.leveldb` 下同一个 Dexie 库 `novel-studio`，**只能由应用自身读写**（leveldb 有 LOCK、且跨 origin 隔离），所以合并全程通过应用实例的 `window.__ns.db` 执行。
- 16 本注册验证书在每份数据集里都是**同标题、不同 id**（`tools/verify-seeds.mjs:227-232` 按标题去重、`create` 里用 `uid()` 生成 id），所以去重必须按 id + 标题双键。
- 各份体量差异真实存在：jfix `olnodes 141 / mubu 29 / lorecats 30`，agent `olnodes 6 / mubu 10 / lorecats 50`，agent 另有 `aipresets 5`、jfix 为 0。
- dev 的实时数据现在在默认位置 `%APPDATA%\小说工坊-dev`（18 本）；`F:\...\小说工坊\小说工坊` 是它 19:23 的旧副本。
- agent / jfix 两份**已有可用指针**（`%APPDATA%\小说工坊-agent-v2-verify`、`小说工坊-jfix` → F: 各自目录），无需我写任何文件即可打开。
- 本次会话对**工作区之外**的文件写入受限（读与删除可行、`cp/mkdir` 被拦），因此备份采用「逻辑备份（JSON，落在工作区内）+ 源目录在验证通过前一律不动」。

## 阶段

### 0. 备份
- 四份数据集各导出**全表 JSON**（含 `works/volumes/chapters/.../aipresets`）到工作区 `tools/_merge-backup-<ts>/`，作为可回滚的逻辑备份。
- 物理目录一律不删，直到第 4 步验证通过。

### 1. 逐份导出（每份启动一次应用实例）
| 数据集 | 启动方式 |
|---|---|
| dev 实时 | `--profile=dev`（默认位置，无指针） |
| agent | `--profile=agent-v2-verify` + `NOVEL_STUDIO_DEV=1`（指针已指向 F:） |
| jfix | `--profile=jfix` + `NOVEL_STUDIO_DEV=1` |
| F: 上那份 dev 旧副本 | 尝试把它复制进一个临时 profile 的默认数据目录再读；若复制被环境拦下则跳过（它与 dev 实时同源、且第 5 步本就要淘汰），并在报告里说明 |

### 2. 归并计算（离线，先出方案再落库）
- 按标题分组，每组算「内容量」= 该作品在各 per-work 表中的**总行数**，取最大者胜出；平手保留 dev 现有那份。
- 产出计划表：每个标题 → `保留 / 用源替换 / 新增`，以及双方的 id 与行数对比，落库前先打印给你看。
- 规则细节：`appconfig` 不合并（各 profile 偏好）；`aipresets` 按 id 叠加、同名已存在则跳过；`airuns` 里 `workId='*'` 的全局用量行不合并。

### 3. 落库到 dev
- `新增`：把该作品在**所有表**里的行（按 workId 过滤，含 `links`/`revisions` 这类无索引表的全表过滤兜底）`bulkPut` 进 dev；
- `用源替换`：先删 dev 该作品的 work + 全部 per-work 行，再整份写入胜出方（整份替换保证双链/批注引用的 id 自洽）；
- 全程走应用自身 Dexie 实例，事务内写；结束后打印每个作品的落库行数。

### 4. 校验
- 作品数 = 各数据集标题并集大小；**无重复标题**；每个源标题都存在；
- 各表行数 ≥ dev 原有值（打印前后对照）；
- 书架实际渲染的标题集合与计算结果一致；抽开 1–2 本验证书进工作台再返回。

### 5. 收尾：只留 dev（你已确认删掉 agent/jfix）
1. 把 dev 的位置落到你期望的 `F:\deepseek workplace\小说工坊\小说工坊`：先把那份旧副本改名为 `_dev-old-<ts>`（保留到最后再删），再用「更改存储位置」指向 `F:\deepseek workplace\小说工坊`，并选**迁移并清理原位置**（清理由新进程在下次启动兑现，我在 dataDir 修复里已经实现）。
2. 删除 `%APPDATA%\小说工坊-agent-v2-verify`、`%APPDATA%\小说工坊-jfix` 两个 profile 目录，以及 `F:\...\小说工坊\agent`、`F:\...\小说工坊\jfix` 两份数据目录。
3. 保留：工作区里的 JSON 备份 + `_dev-old-<ts>`（等你确认合并结果无误后再删）。

### 6. 5 个验收脚本改为跑在 dev 上
`tools/preset-verify.mjs`、`preset-windows-verify.mjs`、`ai-v2-verify.mjs`、`ai-v2-windows-verify.mjs`、`knowledge-verify.mjs`：把隔离断言从「必须 `小说工坊-agent-v2-verify`」改为「必须是 `小说工坊-dev`」（仍然拒绝正式版 profile `小说工坊`，保住原护栏意图），默认 CDP 端口 `9333 → 9222`（保留 `CDP_PORT` 覆盖），并同步注释/报错文案。
验证：对 dev 实例实跑 `preset-verify.mjs` + `preset-windows-verify.mjs`，确认在新 profile 下通过（这两个脚本会为 `preset-work`/`v2-work` 自建夹具，属于预期行为）。

## 风险与回滚

- **不可逆点**只有第 5 步的删除；此前每一步都可回滚（JSON 备份 + 源目录原样保留 + `_dev-old-<ts>`）。
- 同名替换会丢掉 dev 那份的对应内容 —— 这是你选的「内容多的胜出」的直接后果，替换清单会在第 2 步先给你过目。
- 5 个脚本改到 dev 后，它们会**在 dev 数据上建/重置夹具**（`preset-work` 等），这正是"只用 dev 测试"的代价，已在计划内。
- 全程不碰正式版 profile（`%APPDATA%\小说工坊`）与你的真实作品数据。
